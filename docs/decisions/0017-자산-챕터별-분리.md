# ADR-0017: 자산 = 챕터별 hash 디렉터리 분리, 커버 = frontmatter

- **Status**: Accepted (2026-04-26)

## Context

vault 의 책은 폴더별로 `_assets/` 디렉터리를 가짐:
```
books/<책>/Part 1. 파이썬 기초/_assets/p2-foo.png
books/<책>/Part 2. 지식공학/_assets/p2-foo.png    ← 같은 이름, 다른 내용
```

발행 시 자산을 어떻게 배치할지 결정 필요. 사용자 우려: *합칠 거면 hash 변환해야 충돌 안 남*.

## Decision

### 자산 배치 = 챕터별 hash 디렉터리

각 발행 단위 (책 entry, 챕터, 단독 doc) 가 hash 디렉터리를 갖고, 그 안에 `_assets/` 따로:

```
content/
├── kJ7mN2/                      ← 챕터 1 (hash)
│   ├── index.md
│   └── _assets/
│       └── p2-foo.png           ← 이 챕터 참조 이미지만
├── pQ8rT3/                      ← 챕터 2 (hash)
│   ├── index.md
│   └── _assets/
│       └── p2-foo.png           ← 같은 vault 이미지지만 hash 분리되어 충돌 X
└── aB3xK9/                      ← 책 entry (hash)
    ├── index.md
    └── _assets/
        └── book-cover.png
```

**합치지 않으므로 hash 변환 불필요**. 챕터별 hash 디렉터리 자체가 격리.

### 자산 처리 알고리즘

플러그인이 챕터 발행 시:
1. 챕터 markdown 에서 참조된 이미지 ref 추출
2. vault 에서 위치 찾기:
   - 같은 폴더 `_assets/<filename>`
   - 부모 폴더 `_assets/<filename>`
   - vault 전체 search by 파일명
3. `content/<chapter-hash>/_assets/<filename>` 으로 복사
4. markdown 안 이미지 경로 절대화: `<img src="/content/<chapter-hash>/_assets/<filename>" width="...">`

### 책 표지 (cover)

`notedrop-cover` frontmatter 로 지정:

```yaml
---
notedrop-publish: true
notedrop-render: book
notedrop-cover: "_assets/book-cover.png"
---
# 작가의 말
...
```

뷰어 동작:
- `notedrop-cover` 있음: 책 첫 페이지 = 풀블리드 표지 이미지 → 다음 페이지부터 entry 본문 → 이어서 챕터들
- `notedrop-cover` 없음: entry 본문이 1페이지부터 시작 → 이어서 챕터들

표지 이미지도 자산 처리 알고리즘 거침 - entry 의 hash 디렉터리에 복사.

### 지원 포맷

MVP:
- 이미지: png, jpg, jpeg, svg, webp, gif

v2:
- PDF, ZIP 등 비-이미지 자산
- `.excalidraw.md` 파일

미지원 포맷 또는 ref 깨짐:
- 본문에 placeholder ("[이미지 누락: foo.png]")
- warnings 에 기록
- 발행 자체는 계속

### 큰 파일 보호

10MB 초과 이미지: 거부 + 경고. (GitHub 100MB 파일 한도 보호)

## Consequences

긍정:
- 충돌 0 (챕터별 hash 디렉터리 격리)
- 단순 (파일명 변환·hash 부여 로직 불필요)
- vault 의 자산 구조 그대로 보존
- 디버깅 친화 (사람이 봐도 어느 자산이 어느 챕터의 것인지 명확)

부정:
- 같은 vault 이미지가 여러 챕터에서 쓰이면 챕터마다 복사 → 저장 redundancy
- 단 실제 책에서 이런 케이스 흔치 않음. GitHub 1GB 한도 대비 무시 가능

## Alternatives Considered

### 1. 전체 자산 합치기 + hash rename

`content/_assets/<asset-hash>.<ext>` 같은 형태.

거부 사유:
- 디버깅 어려움 (파일명 의미 X)
- 자산 ref 와 실제 파일 매핑 추가 메타 필요

### 2. 전체 자산 합치기 + path-prefix rename

`content/_assets/part-1__foo.png` 같은 형태.

거부 사유:
- 파일명 길어짐
- 한국어 폴더명 인코딩 부담

### 3. 책 단위 자산 (책 hash 디렉터리에)

책 entry 의 `_assets/` 에 모든 챕터 이미지 모음.

거부 사유:
- 챕터끼리 같은 파일명 충돌 (사용자 우려 케이스)
- 챕터 unpublish 시 어느 자산이 어느 챕터의 것인지 추적 부담

### 4. notedrop-cover 없이 항상 entry 본문이 1페이지

거부 사유:
- 책 디자인 자유도 제한 (전통 도서는 표지 이미지 별도)
- 작가가 표지 디자인 의도 표현 못 함
