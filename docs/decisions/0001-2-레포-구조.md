# ADR-0001: 2-레포 구조 (vault private + notedrop public)

- **Status**: Accepted (2026-04-26)
- **Supersedes**: -
- **Superseded by**: -

## Context

이 vault 레포 (`siakun/obsidian-personal`) 는 **private**. 다음 두 가지가 충돌:

1. GitHub Pages 무료 티어는 public 레포만 호스팅 가능 (private Pages 는 GitHub Pro $4/월)
2. 비공개 일기·자아성찰 노트가 같은 vault 에 섞여 있어 사고 시 누설 위험

발행 대상 콘텐츠 (책·공유 문서) 는 어차피 공개라 별도 public 레포로 격리하는 게 자연스럽고 안전.

## Decision

**2-레포 구조** 채택:
- `siakun/obsidian-personal` (현재, private): vault + 플러그인 소스
- `siakun/notedrop` (신규, public): Next.js 뷰어 + 발행된 콘텐츠

플러그인이 발행 시 변환된 마크다운·자산·매니페스트를 두 번째 레포로 git push. GH Actions 가 정적 파일 deploy. 플러그인 설정에 GitHub PAT + 타겟 레포 (owner/name) 입력.

## Consequences

긍정:
- 비공개 누설 리스크 *구조적으로 0*. private 레포에서 public 레포로의 push 코드만 감사하면 됨
- GH Pages 무료 티어 사용 가능
- 콘텐츠 / 작업 공간 분리 명확. private 레포 그대로 옵시디언·일기 워크플로 유지
- public 레포는 사람이 clone 해서 마크다운 직접 읽을 수 있는 형태 (디버깅·백업 친화)
- 미래에 플러그인을 다른 사용자가 자기 vault 에 적용할 때도 같은 패턴 (자기 public 레포 만들면 됨)

부정:
- 플러그인 설정에 GitHub PAT 입력 필요 (UX 한 단계 추가)
- 첫 setup 시 두 레포 wire up 필요 (PAT 발급, 타겟 레포 생성)
- 플러그인이 push 권한 가짐 → PAT 보안 관리 중요 (`saveData()` 만 사용, 콘솔 노출 X)

## Alternatives Considered

### 1. 1-레포 + GitHub Pro

비용 $4/월. 모든 게 `obsidian-personal` 안. private 레포에서 Pages 활성화.

거부 사유:
- 멘탈 모델 헷갈림 (private 레포에서 public Pages 쏘는 구조)
- 사고 위험 (배포 빌드 액션 실수 시 private 콘텐츠 노출 가능성)
- 비용 발생 (개인 프로젝트, 비용 ~0 제약)

### 2. 3-레포 (플러그인 별도)

`siakun/notedrop-plugin` (플러그인 소스) + `siakun/notedrop` (콘텐츠+뷰어) + `siakun/obsidian-personal` (vault).

거부 사유:
- 초기엔 과도한 분리. 플러그인 안정화 전에는 콘텐츠와 뷰어가 함께 진화하는 편이 효율적
- v1.0 안정화 후 community plugins 마켓 등록 시점에 플러그인 분리 검토는 OK (열린 옵션)
