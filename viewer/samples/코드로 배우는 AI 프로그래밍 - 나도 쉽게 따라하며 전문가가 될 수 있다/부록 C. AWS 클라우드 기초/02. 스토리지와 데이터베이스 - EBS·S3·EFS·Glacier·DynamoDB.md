## 1. 스토리지 서비스 지형

AWS 스토리지는 데이터 접근 방식에 따라 크게 **블록 스토리지**와 **객체 스토리지**로 나뉘고, 그 위에 공유 파일 시스템과 장기 아카이브가 얹혀 있습니다.

> [!note] 블록 vs 객체 스토리지
> - **블록 스토리지**: 대용량 파일에서 특정 블록만 수정할 수 있습니다. 속도·랜덤 접근에 유리하고 비용이 상대적으로 높습니다
> - **객체 스토리지**: 파일 단위로 통째 교체합니다. 대용량 저장·HTTP 접근에 유리하고 비용이 상대적으로 낮습니다

| 서비스 | 분류 | 주 용도 | EC2 와의 관계 |
|---|---|---|---|
| **EBS** | 블록 | EC2 부트 볼륨·추가 디스크 | 하나의 EC2 에만 연결 |
| **S3** | 객체 | 파일 저장·정적 웹 호스팅·백업 | EC2 없이도 사용 가능 |
| **EFS** | 파일(NFS) | 여러 EC2 공유 파일 시스템 | 다수의 EC2가 동시 접근 |
| **S3 Glacier** | 객체(아카이브) | 장기 보관·저빈도 접근 | S3 수명 주기로 자동 이동 |

## 2. Amazon EBS (Elastic Block Store)

### 2.1 정의와 특성

> [!note] Amazon EBS
> EC2 인스턴스에 연결해 쓰는 **영구 블록 스토리지** 입니다. EC2 전원 차단·연결 해제 뒤에도 데이터가 유지됩니다. 고가용성·내구성을 보장하며, 가용 영역(AZ) 내에서 자동 복제됩니다. PC의 SSD·HDD 하드디스크에 해당합니다.

핵심 제약은 **EBS 볼륨이 하나의 EC2 인스턴스에만 연결된다**는 점입니다(동일 AZ 조건). 여러 EC2에서 공유하고 싶다면 EFS를 씁니다.

### 2.2 볼륨 유형

| 유형 | 분류 | 특징 | 용도 |
|---|---|---|---|
| 범용 SSD (gp2 / gp3) | SSD | 기본형, 대부분의 워크로드 커버 | EC2 부트 볼륨, 일반 서버 |
| 프로비저닝된 IOPS SSD (io1 / io2) | SSD | 보장된 고 IOPS, 최고 성능·최고 비용 | 고성능 DB, 트랜잭션 |
| 처리량 최적화 HDD (st1) | HDD | 대용량 순차 처리 | 빅데이터, 로그 스트리밍 |
| 콜드 HDD (sc1) | HDD | 저비용, 드물게 접근 | 저빈도 대용량 저장 |
| 마그네틱 (standard) | (구형) | 현재는 잘 쓰지 않음 | (권장 안 함) |

HDD 계열은 AWS에서 **부트 볼륨으로 지정할 수 없습니다**. EC2를 만들 때는 기본 gp SSD로 부트 볼륨을 만들고, HDD는 추가 디스크로만 붙입니다.

### 2.3 스냅샷과 추가 기능

> [!note] 스냅샷(Snapshot)
> 특정 시점 EBS 볼륨 상태를 저장하는 백업 기능입니다. 최초 한 번은 전체를 저장(기준 스냅샷), 이후에는 변경분만 증분 저장합니다. 스냅샷은 내부적으로 **S3에 저장** 되며, 다른 리전으로 복사해 지역 이중화도 가능합니다.

| 기능 | 설명 |
|---|---|
| 스냅샷 | 증분 백업, 원하는 시점으로 복원 가능 |
| 암호화 | 볼륨·스냅샷 모두 KMS 기반 암호화 지원 |
| 타 리전 복사 | 스냅샷을 다른 리전으로 이전 가능 |
| 탄력성 | **EC2 중지 없이** 용량 확장·유형 변경 가능 (OS 레벨 파티션 확장 작업은 별도 필요) |
| AMI 연계 | EC2 백업(AMI) 생성 시 연결된 EBS가 함께 스냅샷됩니다 |

### 2.4 요금 구조

- **기본 요금**: 프로비저닝한 용량(GB) x 월 단가. 유형별 단가 상이
- **gp SSD / io SSD**: 용량 요금에 IOPS 트래픽이 포함
- **마그네틱·HDD**: 용량 + **I/O 요청 횟수** 별 추가 과금
- **스냅샷**: S3 저장 요금 기준
- **데이터 전송**: 인바운드는 거의 무료, 외부 송신·타 리전 전송은 과금

### 2.5 EBS 볼륨 생성·연결·마운트·삭제

콘솔 경로: **EC2 대시보드 -> Elastic Block Store -> 볼륨 -> 볼륨 생성**

1. 볼륨 유형 선택 (기본 gp3 권장)
2. 용량 지정 (1 GB ~ 16 TB). 예시는 10 GB
3. **가용 영역 선택**: 연결할 EC2와 동일한 AZ 여야 합니다
4. (선택) 기존 스냅샷으로부터 생성, 암호화, 태그 설정
5. 볼륨 생성 -> 작업 메뉴에서 "볼륨 연결" -> 대상 EC2 인스턴스와 디바이스 이름 지정

EC2에 SSH 접속한 뒤 파일 시스템 생성·마운트:

```bash
# 1. 새로 붙은 디바이스 확인
ls -l /dev/sdf
# Nitro 인스턴스에서는 보통 /dev/nvme1n1로 보입니다

# 2. 파일 시스템 생성
sudo mkfs -t ext4 /dev/nvme1n1

# 3. 마운트 포인트 생성 후 마운트
sudo mkdir -p /mnt/ebs
sudo mount /dev/nvme1n1 /mnt/ebs

# 4. 사용 확인 (10 GB 중 대략 9.2 GB 가용)
df -h /mnt/ebs
```

삭제 절차: 콘솔에서 **강제 분리**(또는 OS에서 `umount` 후 분리) -> 볼륨 삭제. 실습 후에는 비용 방지를 위해 반드시 삭제하세요.

## 3. Amazon S3 (Simple Storage Service)

### 3.1 정의와 특성

> [!note] Amazon S3
> 객체 스토리지 서비스입니다. **버킷(bucket)** 이라는 최상위 컨테이너에 파일(객체)을 업로드해 HTTP(S) 로 접근합니다. 99.999999999% (11 개의 9) 내구성이 목표이며, 용량 사전 지정이 불필요하고 쓴 만큼 과금합니다.

| 속성 | 값 / 특징 |
|---|---|
| 단일 객체 최대 크기 | 5 TB (Multipart Upload 사용 시) |
| 객체 개수 제한 | 사실상 무제한 |
| 내구성 | 여러 시설(AZ)에 중복 저장 |
| 접근 방법 | 콘솔, HTTPS URL, AWS CLI, SDK (boto3·Java·Node.js 등) |

### 3.2 스토리지 클래스 6 종

| 클래스                                                   | 용도                       | 특징                        |
| ----------------------------------------------------- | ------------------------ | ------------------------- |
| **S3 Standard**                                       | 일반 파일 저장, 잦은 접근          | 기본값, 고성능·고가용              |
| **S3 Intelligent-Tiering**                            | 접근 패턴이 불확실한 데이터          | 모니터링 후 자동으로 저비용 계층으로 이동   |
| **S3 Standard-IA** (Infrequent Access)                | 빠른 접근이 필요하나 빈도가 낮음       | Standard보다 저렴, 조회 시 요금 발생 |
| **S3 One Zone-IA**                                    | 한 AZ에만 저장해도 되는 복제 가능 데이터 | 다중 AZ 중복 없음, 가장 저렴한 IA    |
| **S3 Glacier Flexible Retrieval / Instant Retrieval** | 아카이빙                     | 저비용, 조회 지연 (즉시·분·시간 단위)   |
| **S3 Glacier Deep Archive**                           | 장기 아카이빙                  | 최저 비용, 조회 지연이 가장 큼        |

### 3.3 버킷·객체·접근 URL

- 버킷 이름은 **AWS 글로벌 전체에서 유일** 해야 합니다 (DNS 네이밍 규칙)
- 리전을 지정해 생성하며, 서비스 대상 지역 근처로 고르면 지연을 줄일 수 있습니다
- 객체 URL 형식은 두 가지입니다
    - 가상 호스트 방식: `https://<bucket>.s3.<region>.amazonaws.com/<key>`
    - 경로 방식: `https://s3.<region>.amazonaws.com/<bucket>/<key>`
- 기본 권한은 **비공개** 입니다. 퍼블릭 정적 웹 호스팅을 하려면 "모든 퍼블릭 액세스 차단" 해제 후 버킷 정책을 설정해야 합니다

### 3.4 폴더·객체 key 이해

S3 에는 엄밀히 말해 폴더 개념이 없습니다. 콘솔에서는 폴더처럼 보이지만 실체는 key 이름에 슬래시가 포함된 단일 객체입니다.

> [!example] key 구조
> `testfolder/notes.csv` 라는 객체를 업로드하면 testfolder 폴더가 있는 것처럼 보이지만, 실체는 key 문자열에 `/`가 들어간 단일 객체입니다. SDK로 업로드할 때 `/`를 포함한 key를 주면 자동으로 그런 계층이 만들어집니다.

### 3.5 주요 활용 사례

- 정적 웹사이트 호스팅 (HTML·CSS·JavaScript 만으로 구성된 사이트)
- 백업·재해 복구 (EBS 스냅샷도 내부적으로 S3 저장)
- 빅데이터 수집 저장소 (CCTV·앱 업로드 등을 SDK로 직접 put)
- AI 학습 데이터·모델 아티팩트 저장 (전이학습 가중치, TFLite 모델 등)
- 클라우드 스토리지 (Dropbox 형태와 유사한 서비스)
- 리전 간 복제, Access Point를 통한 다지역 빠른 접근

### 3.6 요금 구조

- **저장 용량**: GB 단위 월 과금 (클래스별 단가 차등)
- **요청**: PUT, COPY, POST, LIST, GET 등 요청 횟수별 소액 과금
- **데이터 전송**: 업로드는 무료. 같은 리전 내 CloudFront·EC2 간 전송은 무료. 인터넷 송출은 과금
- **팁**: 같은 리전의 EC2에서 S3 데이터를 처리하면 통신 비용이 발생하지 않습니다

### 3.7 버킷 생성 실습

콘솔 경로: **S3 -> 버킷 만들기**

| 항목 | 내용 |
|---|---|
| 버킷 이름 | 전역 유일, DNS 호환 |
| 리전 | 가까운 리전 선택 |
| 기존 버킷 설정 복사 | 동일 설정 재사용 가능 |
| ACL 권한 | 비활성 권장 (버킷 단위 정책 사용). 개별 객체 권한이 필요하면 활성 |
| 모든 퍼블릭 액세스 차단 | 기본 차단. 정적 웹 호스팅 시만 해제 |
| 버전 관리 | 파일 변경 이력·롤백 |
| 기본 암호화 | 업로드되는 모든 객체에 기본 암호화 적용 가능 |

업로드: 버킷 진입 -> 업로드 -> 파일 추가 -> 업로드 버튼. 콘솔의 기본 다운로드는 단일 파일 단위이므로 다수 파일은 CLI·SDK로 처리합니다.

### 3.8 AWS CLI로 S3 다루기

AWS CLI 설치 후 `aws configure`로 IAM에서 발급한 Access Key ID·Secret Access Key를 등록합니다. 자격 증명 설정 절차는 다음 장의 `3. AWS CLI와 IAM 사용자`에서 다시 다룹니다.

```bash
# 보유 버킷 목록
aws s3 ls

# 특정 버킷의 파일 목록
aws s3 ls s3://my-test-bucket

# 버킷 전체를 현재 디렉터리로 복사 (다운로드)
aws s3 cp s3://my-test-bucket . --recursive

# 로컬 파일 업로드
aws s3 cp local_file.txt s3://my-test-bucket/

# 변경된 파일만 동기화
aws s3 sync ./local_dir s3://my-test-bucket/remote_prefix/
```

### 3.9 boto3로 S3 다루기

파이썬에서는 `boto3`가 표준입니다.

```python
import boto3

s3 = boto3.client("s3")

# 객체 목록 조회
resp = s3.list_objects_v2(Bucket="big-data-center")
for obj in resp.get("Contents", []):
    print(obj["Key"], obj["Size"])

# 업로드·다운로드
s3.upload_file("file.jpg", "big-data-center", "path/file.jpg")
s3.download_file("big-data-center", "path/file.jpg", "downloaded.jpg")
```

## 4. Amazon EFS (Elastic File System)

### 4.1 정의와 특성

> [!note] Amazon EFS
> **완전 관리형** 공유 파일 스토리지입니다. NFS v4 프로토콜로 여러 EC2가 동시에 마운트해 공유 파일 시스템으로 사용합니다. 용량·성능을 자동으로 스케일하며 사전 지정이 필요 없습니다.

> [!info] 관리형 vs 완전 관리형
> - **관리형**: AWS가 인프라만 제공, 사용자가 인스턴스 내부 설정·운영 담당 (예: EC2)
> - **완전 관리형**: 사용자는 사용만, 인프라·용량·성능은 AWS가 자동 관리 (예: S3, EFS, Lambda)

### 4.2 주요 설정 항목

| 항목 | 설명 |
|---|---|
| VPC | 연결할 EC2와 동일 VPC |
| 서브넷·가용 영역 | 각 AZ 마다 하나의 마운트 타겟 |
| 보안 그룹 | NFS 포트 **TCP 2049** 허용 필요 |
| 스토리지 클래스 | 다중 AZ(권장) 또는 One Zone(테스트·비용 절감) |
| 성능 모드 | 범용(기본) 또는 Max I/O |
| 암호화 | 저장 시 암호화 옵션 제공 |

### 4.3 보안 그룹 구성 패턴

두 개의 보안 그룹이 쌍으로 동작합니다.

- **EC2 SG** (예: demo-linux-sg)
    - 인바운드: SSH 22 번, NFS 2049 번 (Source: demo-efs-sg)
- **EFS SG** (예: demo-efs-sg)
    - 인바운드: NFS 2049 번 (Source: demo-linux-sg)

서로의 SG를 Source로 참조해 닫힌 루프를 만드는 패턴입니다.

### 4.4 EFS 생성·마운트 실습

콘솔 경로: **EFS -> 파일 시스템 -> Create file system**

1. VPC·서브넷·AZ·보안 그룹 선택
2. 성능 모드·암호화 선택 후 생성
3. 마운트 타겟 생성 대기 (3 ~ 5 분)
4. 좌측 "Amazon EC2 mount instructions" 에서 지침 확인
5. EC2의 보안 그룹 인바운드에 2049 포트 추가

EC2에서 마운트 (Amazon Linux는 `amazon-efs-utils` 사전 설치):

```bash
# 1. 마운트 포인트 생성
sudo mkdir -p /mnt/efs

# 2. EFS 마운트 (file system id는 콘솔에서 확인)
sudo mount -t efs fs-0123456789abcdef0:/ /mnt/efs

# Ubuntu 등에서 amazon-efs-utils 미설치 시 표준 NFS 명령
# sudo mount -t nfs4 -o nfsvers=4.1,rsize=1048576,wsize=1048576,hard,timeo=600,retrans=2,noresvport \
#   fs-xxx.efs.ap-northeast-2.amazonaws.com:/ /mnt/efs

# 3. 여러 EC2에서 동일 경로 마운트 시 파일 공유 확인
echo "test from EC2-A" | sudo tee /mnt/efs/test.txt
# 다른 EC2에서 cat /mnt/efs/test.txt로 동일 내용 확인
```

정리: `sudo umount /mnt/efs` 후 콘솔에서 파일 시스템 삭제.

### 4.5 EBS·S3·EFS 한눈에 비교

| 항목 | EBS | S3 | EFS |
|---|---|---|---|
| 타입 | 블록 | 객체 | 파일(NFS) |
| 공유 | 1 EC2 전용 | 모든 서비스 | 다수 EC2 공유 |
| 용량 지정 | 사전 프로비저닝 | 무한·자동 | 자동 |
| 과금 단위 | 프로비저닝 용량 | 실사용 용량 + 요청 | 실사용 용량 |
| 비용 수준 | 중 | 저 | 상대적으로 높음 |
| 접근 프로토콜 | 블록 디바이스 | HTTPS·S3 API | NFS |

> [!warning] EC2 "종료" 는 인스턴스 삭제
> EC2 작업 메뉴의 "중지(Stop)" 는 전원 off, "**종료(Terminate)**" 는 인스턴스 **삭제** 입니다. 종료 시 루트 EBS가 함께 삭제되는지 안내 메시지를 반드시 확인하세요. 백업이 필요하면 스냅샷·AMI를 먼저 생성합니다.

## 5. Amazon S3 Glacier

### 5.1 정의와 특성

> [!note] Amazon S3 Glacier
> 장기 아카이빙(보관) 목적의 저비용 객체 스토리지입니다. S3와 같은 높은 내구성을 공유하지만 조회 속도가 느리고 대신 매우 저렴합니다. 데이터는 **볼트(Vault)**에 저장되며, 마그네틱 테이프를 대체하는 용도로 설계되었습니다.

주요 용도는 의료 영상, 미디어 원본 아카이브, 규제 준수용 장기 보관 기록, 연도별 업무 로그 백업 등입니다.

### 5.2 검색(Retrieval) 옵션

Glacier는 평균 지연이 분에서 시간 단위로, S3 Standard의 즉시 조회와 다릅니다. 필요한 속도에 따라 옵션을 선택합니다.

| 옵션 | 지연 | 비용 |
|---|---|---|
| 신속(Expedited) | 1 ~ 5 분 | 가장 비쌈 |
| 표준(Standard) | 3 ~ 5 시간 | 기본 |
| 대량(Bulk) | 5 ~ 12 시간 | 가장 저렴 |

초기 Glacier 에는 신속 옵션이 없었으나, 빠른 복구 수요를 반영해 추가되었습니다.

### 5.3 S3 vs Glacier 요약

| 항목 | S3 (Standard) | S3 Glacier |
|---|---|---|
| 데이터 볼륨 | 제한 없음 | 제한 없음 |
| 평균 조회 지연 | 밀리초 | 분 ~ 시간 |
| 단일 객체 최대 | 5 TB | 40 TB (아카이브 단위) |
| 기본 암호화 | 옵션 (추가 설정) | 기본 제공 |
| 비용 | 보통 | 가장 낮음 |
| 과금 대상 | 저장 + 모든 요청 | 저장 + 업로드·검색 요청 |

### 5.4 수명 주기(Lifecycle) 정책

S3 -> Glacier -> 삭제로 이어지는 자동 이전을 수명 주기 규칙으로 설정할 수 있습니다.

> [!example] 전형적인 수명 주기 흐름
> 1. 업로드 직후: **S3 Standard** (잦은 접근)
> 2. 30 일 경과: **S3 Standard-IA** (빈도 하락)
> 3. 90 일 경과: **S3 Glacier** (아카이빙)
> 4. 7 년 경과: 만료 (삭제)

### 5.5 Vault 생성 실습

콘솔 경로: **S3 Glacier -> 저장소 생성(Create vault)**

1. 리전 선택
2. 저장소(Vault) 이름 지정 (예: compliance-2026)
3. 이벤트 알림 옵션 (SNS 토픽 연계해 아카이브 업로드·삭제 이벤트 알림 가능)
4. 검토 후 제출

Vault는 콘솔에서 파일 업로드 UI를 제공하지 않으며, 다음 중 한 가지 방법으로 데이터를 넣습니다.

- **AWS CLI**: `aws glacier upload-archive ...`
- **SDK** (Java·.NET·Python 등)
- **S3 수명 주기 정책**: 볼트의 ARN을 지정해 조건 충족 시 자동 이전
- 서드파티 백업 도구

### 5.6 보안·암호화

Glacier는 저장 시 **기본 암호화**가 항상 적용되지만, S3는 별도 설정이 필요하다는 차이가 있습니다. IAM 기반 접근 제어는 두 서비스 모두 동일하게 적용됩니다.

> [!warning] Glacier 오용 주의
> Glacier는 저장 비용이 극도로 저렴한 대신 **액세스 비용이 비쌉니다**. 자주 꺼내 보는 데이터를 Glacier에 두면 오히려 일반 S3보다 총 비용이 훨씬 늘어납니다. 데이터의 액세스 패턴을 먼저 분석한 뒤 스토리지 클래스를 고르세요.

## 6. AWS 데이터베이스 관리 모델 비교

AWS에서 DB를 운영하는 방식은 관리 범위에 따라 단계가 나뉩니다. 관리 책임이 AWS 쪽으로 많이 이양될수록 사용자는 애플리케이션 로직에만 집중할 수 있습니다.

| 구분 | 예시 서비스 | 사용자가 관리할 항목 |
|---|---|---|
| 온프레미스 | 자체 서버 + DBMS 직접 설치 | 하드웨어, OS 설치·패치, DBMS 설치·패치, 백업, 확장성, 보안, 애플리케이션 |
| 비관리형 (EC2 위 DB) | EC2 + MySQL 수동 설치 | OS 패치, DBMS 설치·패치, 백업, 확장성, 애플리케이션 |
| 관리형 | RDS (MySQL·PostgreSQL·Oracle·MS SQL·MariaDB·Aurora) | 일부 보안(서브넷·포트·엔드포인트), 애플리케이션 |
| 완전 관리형 | DynamoDB, Aurora Serverless, Redshift Serverless | 애플리케이션만 (인스턴스·스토리지 세팅 불필요) |

> [!note] 관리 모델의 핵심 차이
> 관리형(RDS)은 내부적으로 EC2 인스턴스 위에서 동작하므로 사용자가 인스턴스 클래스·스토리지 용량을 지정합니다. 완전 관리형(DynamoDB, Aurora Serverless)은 인스턴스 개념 없이 테이블·사용량만으로 과금됩니다.

## 7. Amazon RDS (Relational Database Service)

### 7.1 특징

RDS는 관계형 DBMS를 AWS가 관리형으로 제공하는 서비스입니다. EC2 인스턴스와 전용 스토리지가 묶여 하나의 DB 인스턴스로 생성되며, 사용자는 DBMS 엔진을 선택하기만 하면 OS·DBMS 설치가 자동 수행됩니다.

지원 엔진:

- MySQL
- PostgreSQL
- MariaDB
- Oracle
- Microsoft SQL Server
- Amazon Aurora (MySQL·PostgreSQL 호환)

### 7.2 고가용성 구성

> [!info] 다중 AZ 배포 (Multi-AZ)
> 서로 다른 가용 영역 두 곳에 RDS 인스턴스를 동기식으로 복제합니다. 주 인스턴스 장애 시 자동으로 대기 인스턴스로 failover 합니다. RDS 생성 시 옵션 한 번으로 활성화됩니다.

> [!info] 읽기 전용 복제본 (Read Replica)
> 엔드포인트가 Writer(읽기·쓰기)와 Reader(읽기 전용) 두 개로 제공됩니다. 애플리케이션이 쓰기는 Writer, 조회는 Reader로 분산하면 부하·지연이 감소합니다. 다른 리전으로도 복제할 수 있습니다.

### 7.3 사용 사례와 한계

**적합한 워크로드**: 웹·모바일 애플리케이션, 전자상거래, 모바일·온라인 게임.

> [!warning] RDS가 부적합한 경우
> - 초당 읽기 15,000 회 + 쓰기 15,000 회(약 30,000 IOPS)를 넘는 초고성능 트래픽 (고성능 io 볼륨·Aurora 고려)
> - NoSQL 형태 데이터 (DynamoDB 사용)
> - AWS가 엔진으로 제공하지 않는 DBMS (EC2에 직접 설치)

### 7.4 비용 구성 요소

| 요소 | 과금 방식 |
|---|---|
| 엔진(인스턴스 타입) | 시간당 (CPU·메모리 기반). 전체 비용에서 가장 큰 비중 |
| 스토리지 | 프로비저닝한 용량 기준 (Aurora는 사용량 기반 자동 확장) |
| 구매 옵션 | 온디맨드(시간당) vs 예약 인스턴스(기간 약정, 선불 할인) |
| 백업 스토리지 | 활성 DB 크기의 100% 까지 무료, 초과·중지 상태 스토리지는 GB 당 과금 |
| 네트워크 I/O | 인바운드 무료, 아웃바운드만 과금 |
| 인스턴스 수 | Read Replica 추가 시 각각 별도 과금 |

## 8. RDS·Aurora 실습

### 8.1 인스턴스 생성 플로우

1. RDS 콘솔, 데이터베이스 생성
2. 생성 방식: "손쉬운 생성" vs "표준 생성" (옵션 상세 제어는 표준)
3. 엔진 선택: 예를 들어 Aurora MySQL 호환 버전
4. 템플릿: 프로덕션 / 개발·테스트 / 프리 티어
5. DB 이름, 마스터 사용자·비밀번호
6. 인스턴스 클래스: 개발·테스트용은 `t3.small` 이상 권장. 더 작은 버스터블은 체감 지연이 큽니다
7. 다중 AZ 배포 체크
8. VPC·서브넷·보안 그룹 선택
9. 퍼블릭 액세스: 외부 접근이 필요하면 "예"
10. 암호 인증(기본) 또는 IAM 데이터베이스 인증
11. 추가 구성: 모니터링, 백업, 오토 스케일링, 유지관리
12. **삭제 방지 옵션**: 실서비스에서는 반드시 체크

> [!warning] RDS 중지의 함정
> RDS 인스턴스를 "중지" 해도 약 1 주일 뒤 자동으로 재가동됩니다. 장기간 중단이 필요하면 스냅샷 저장 후 삭제가 실용적입니다.

### 8.2 MySQL Workbench로 접속

1. 인스턴스 상세에서 엔드포인트 URL 복사
2. 보안 그룹 인바운드 규칙에 3306 포트가 열려 있는지 확인 (필요 시 "내 IP" 옵션으로 소스 제한)
3. MySQL Workbench 실행, 새 Connection
    - Hostname: 복사한 엔드포인트
    - Port: 3306
    - User: 생성 시 지정한 마스터 사용자
4. 연결 성공 시 시스템 스키마 확인 가능, 추가 스키마·테이블 생성

### 8.3 Aurora 특징

- MySQL·PostgreSQL과 호환되는 AWS 자체 관계형 엔진입니다
- 스토리지 사전 프로비저닝 불필요 (사용량에 따라 자동 확장, S3와 유사)
- 서버리스 모드 제공 (인스턴스 클래스 지정도 불필요)
- 3 개 가용 영역에 데이터 복제, 최대 15 개까지 읽기 전용 복제본 생성 가능

## 9. Amazon DynamoDB

### 9.1 NoSQL 기본 개념

> [!note] 관계형 vs 비관계형
> 관계형 DB는 행·열 스키마가 고정되어 있고 SQL로 CRUD를 수행합니다. 비관계형 DB는 키-값 기반으로 스키마가 동적이며, 항목마다 속성이 달라도 됩니다.

비관계형의 장점:

- 스키마가 고정되지 않아 새 속성 추가 시 ALTER가 불필요합니다
- 특정 항목에 값이 없으면 필드 자체를 생략할 수 있습니다
- 데이터 타입이 동적입니다 (같은 필드도 항목별로 타입이 다를 수 있습니다)
- 빅데이터·비정형 데이터에 유리합니다

### 9.2 DynamoDB 특성

- 완전 관리형 NoSQL 서비스 (인스턴스 개념 없음, S3 처럼 사용량 기반)
- 모든 데이터를 SSD에 저장
- 여러 가용 영역에 자동 복제 (고가용성)
- 제약 없는 스토리지·처리량
- 기본 키 구성:
    - **파티션 키**(단일 키, 필수)
    - **파티션 키 + 정렬 키**(복합 키, 선택)
- 데이터가 일정 크기 이상 쌓이면 자동 파티셔닝으로 조회 속도를 유지합니다

### 9.3 테이블 생성 실습

1. DynamoDB 콘솔 -> 테이블 생성
2. 테이블 이름: `ProductCatalog`
3. 파티션 키: `Id` (타입 숫자)
    - 주입할 JSON 파일의 키 이름과 정확히 일치해야 합니다
4. 정렬 키: 선택 (예시에서는 미지정)
5. 용량·오토 스케일링·암호화는 기본 설정
6. 테이블 생성

### 9.4 CLI로 데이터 주입

CLI 설정이 끝났다면 다음 명령으로 기본 조작이 가능합니다.

```bash
# 테이블 목록
aws dynamodb list-tables --region ap-northeast-2

# 테이블 상세 (크기, 파티션 키, 아이템 수 등)
aws dynamodb describe-table --table-name ProductCatalog --region ap-northeast-2

# JSON 파일로 일괄 쓰기
aws dynamodb batch-write-item \
  --request-items file://ProductCatalog.json \
  --region ap-northeast-2

# 키로 단일 조회
aws dynamodb get-item \
  --table-name ProductCatalog \
  --key '{"Id":{"N":"201"}}' \
  --region ap-northeast-2

# 전체 스캔
aws dynamodb scan --table-name ProductCatalog --region ap-northeast-2
```

**배치 주입 JSON 구조 예시**:

```json
{
  "ProductCatalog": [
    {
      "PutRequest": {
        "Item": {
          "Id": {"N": "101"},
          "Title": {"S": "Book 101 Title"},
          "Price": {"N": "2"}
        }
      }
    }
  ]
}
```

정상 처리 시 `UnprocessedItems: {}` 응답이 옵니다. 에러가 나면 주로 키 이름·타입 불일치입니다.

### 9.5 NoSQL 저장 구조의 시각화

DynamoDB 콘솔은 데이터를 표로 표시하지만, 실제 저장은 각 아이템이 자기 속성만 갖는 형태입니다. 콘솔 표에서 빈 칸으로 보이는 필드는 실제로는 저장 자체가 안 된 상태입니다.

## 10. Amazon Redshift

### 10.1 특징

Redshift는 관계형 SQL DB 이지만 RDS와 달리 **완전 관리형 데이터 웨어하우스** 입니다. EC2 인스턴스가 아니라 클러스터 구조의 테이블 저장소를 만들고 그 안에 데이터를 쌓습니다.

- 열 기반(Columnar) 스토리지, 대용량 분석 쿼리에 최적화
    - 일반 RDBMS는 행 기반 저장이라 행 전체를 빠르게 읽고 쓰는 데 강합니다
    - Redshift는 특정 열 집계·분석 쿼리에서 훨씬 효율적입니다
- 병렬 처리(MPP, Massively Parallel Processing) 구조
- 리더 노드 + 컴퓨트 노드 구성, 리더는 고가용성 구성 제공
- 백업은 내부 SSD·S3 기반
- JDBC·ODBC 드라이버 제공, 표준 SQL 지원

### 10.2 클러스터 생성 모드

- **프로비저닝된 클러스터**: 노드 개수·타입을 직접 지정하는 전통 방식
- **Redshift Serverless**: 노드 관리 불필요. VPC·서브넷·보안 설정은 사전 구성 필요

### 10.3 실습 흐름

1. Redshift 콘솔에서 클러스터 생성
    - 사용 목적: 프로덕션 / 무료 평가판(학습용)
    - 관리자 ID·비밀번호 지정
2. 클러스터 생성 완료 후 "쿼리 편집기" 진입
3. 샘플 테이블(category, date 등) 기준으로 SELECT 테스트
4. 외부 애플리케이션에서 접근 시 JDBC·ODBC 드라이버 다운로드 후 사용

> [!warning] Redshift Serverless 생성 실패
> Redshift Serverless는 VPC·서브넷·보안 설정이 선행되어야 생성이 완료됩니다. 처음에는 프로비저닝 모드 먼저 다루는 것이 안정적입니다.

## 11. DBMS 선택 가이드

실무에서 DB를 고를 때 참고할 수 있는 요약 표입니다.

| 요구사항 | 권장 서비스 |
|---|---|
| 일반적인 관계형 DB, 다양한 엔진 선택 | RDS |
| AWS 관리형 관계형 DB, MySQL·PostgreSQL 호환, 고성능 필요 | Aurora (RDS 내부에서 선택) |
| 예측 불가한 트래픽, 서버리스 관계형 필요 | Aurora Serverless |
| 비정형 데이터, 단일 자리수 ms 응답, 수평 확장 | DynamoDB |
| 페타바이트급 분석·데이터 웨어하우스 | Redshift |
| AWS가 제공하지 않는 DBMS | EC2 인스턴스에 직접 설치 |

## 12. AI 파이프라인과 스토리지·DB 선택

본편에서 만든 AI 파이프라인을 AWS에 얹을 때, 구성 요소별로 어떤 저장소·DB를 고르는 것이 자연스러운지 정리합니다.

| AI 파이프라인 구성 | 권장 저장소 | 이유 |
|---|---|---|
| 학습 데이터(이미지·텍스트·csv) | **S3** | 저렴한 객체 저장, 라이브러리가 S3 URI를 직접 지원 |
| 학습 중간 체크포인트 | S3 | 다중 머신에서 공유, 실패 시 재개 |
| 모델 아티팩트(`.h5`·`.tflite`·`.joblib`) | S3 | 버전 관리·배포 | 
| 실시간 추론 캐시·피처 저장 | **DynamoDB** | ms 단위 응답, 스키마리스 |
| 과거 로그·사용자 이력 | RDS 또는 Aurora | 관계형 분석 쿼리 필요 시 |
| 대규모 분석·리포팅 | Redshift | 열 기반 집계 쿼리에 최적 |
| 학습 머신 로컬 작업 디스크 | **EBS** | EC2에 직접 붙는 블록 스토리지 |
| 여러 학습 머신이 공유하는 데이터셋 캐시 | EFS | 다중 EC2 동시 마운트 |
| 완료된 원본 데이터·규제 보관 | S3 Glacier | 저비용 장기 보관 |

Ch 03 에서는 여기에 EC2·Cloud9·Lambda를 더해 "업로드 -> 처리 -> 저장 -> 재조회" 의 통합 파이프라인을 실제로 돌려 봅니다.

## 13. 실습 리소스 정리 체크리스트

이 챕터 실습을 마치면 다음 항목을 확인해 삭제하세요. 누락된 리소스가 있으면 Free Tier 범위를 벗어나 지속 과금됩니다.

- [ ] EBS 볼륨: 연결 해제 후 삭제
- [ ] EBS 스냅샷: 필요 없으면 삭제 (용량에 비례해 S3 요금 발생)
- [ ] S3 버킷: 객체를 비운 후 버킷 삭제
- [ ] EFS 파일 시스템: 모든 마운트 타겟 삭제 -> 파일 시스템 삭제
- [ ] Glacier Vault: 아카이브 삭제 후 Vault 삭제
- [ ] RDS 인스턴스: 삭제 방지 해제 -> 스냅샷 옵션 선택 -> 삭제
- [ ] DynamoDB 테이블: 삭제
- [ ] Redshift 클러스터: 최종 스냅샷 옵션 선택 -> 삭제

## 14. 마무리

- AWS 스토리지는 **EBS(블록) · S3(객체) · EFS(파일) · Glacier(아카이브)** 네 종으로 각각의 접근 패턴에 맞게 골라야 합니다
- AWS 데이터베이스는 **RDS·Aurora(관계형) · DynamoDB(NoSQL) · Redshift(웨어하우스)**로 축이 나뉩니다
- 완전 관리형 수준이 높을수록 사용자의 관리 부담이 줄지만 커스터마이징 자유도는 낮아집니다. 비용·관리 부담·성능을 함께 비교해 결정합니다
- AI 파이프라인에서는 대체로 **데이터·모델 저장은 S3**, **실시간 피처·캐시는 DynamoDB**, **학습 머신 디스크는 EBS**가 기본 조합입니다
- Free Tier 내에서 실습하려면 크기·시간 한도를 지키고, 실습 종료 시 리소스를 반드시 정리하세요
