## 1. 클라우드 컴퓨팅의 정의

AWS가 제시하는 클라우드 컴퓨팅의 정의는 한 문장입니다.

> [!note] 클라우드 컴퓨팅 (Cloud Computing)
> 컴퓨터 파워, 데이터베이스, 스토리지, 애플리케이션, 그 밖의 IT 리소스를 **인터넷을 통해 온디맨드(on-demand)로 제공** 하고, **사용한 만큼 지불(pay-as-you-go)** 하는 것.

핵심 키워드 두 개는 온디맨드 제공과 사용량 기반 과금입니다. 리소스가 물리적으로 어느 데이터 센터에 있는지는 사용자가 알 필요가 없고, AWS 내부에서도 정확한 위치를 대외에 공개하지 않습니다. 클라우드라는 단어가 주는 "구름" 느낌은 바로 이 추상화, 즉 위치·하드웨어의 은닉에서 나옵니다.

> [!warning] 클라우드의 이점을 살리지 못하는 설계
> 초기에 넉넉하게 프로비저닝해 두고 실제로는 대부분을 놀리고 있다면, 그것은 "낭비가 일어나도록 설계한 아키텍처" 입니다. 사용한 만큼만 내는 구조를 제대로 쓰지 못하면 클라우드의 경제적 이점이 사라집니다.

## 2. 인프라 관점의 전환 - 하드웨어에서 소프트웨어로

전통적인 온프레미스 인프라와 클라우드 인프라의 차이를 한 표로 정리합니다.

| 구분 | 온프레미스 | 클라우드 |
|---|---|---|
| 인프라 성격 | 하드웨어 솔루션 | 소프트웨어처럼 다룸 |
| 공간·보안·전력 | 물리 시설을 직접 확보 | AWS가 담당 |
| 자본지출 | 대규모 선투자 | 가변 비용 |
| 구매·설치 주기 | 수 주에서 수 개월 | 수 분, 클릭 몇 번 |
| 용량 산정 | 피크를 추정해 과대 프로비저닝 | 온디맨드 자동 조정 |
| 변경 속도 | 느림 | 민첩 |

전통 방식은 "최대 피크를 추정해 용량을 확보" 해야 합니다. 예를 들어 수강 신청 서버는 1년에 두 번만 트래픽이 폭증하는데, 그 피크를 감당하려고 1년 내내 놀고 있는 고사양 장비를 사 두는 식입니다. 클라우드는 평상시 작은 리소스로 운영하다가 피크 시점에 자동 확장하고, 트래픽이 빠지면 축소합니다.

## 3. 서비스 모델 - IaaS·PaaS·SaaS

> [!note] 클라우드 서비스 모델 3 가지
> - **IaaS (Infrastructure as a Service)**: 가상 서버, 스토리지, 네트워크 같은 인프라 자원을 서비스로 제공합니다. 예: Amazon EC2
> - **PaaS (Platform as a Service)**: 애플리케이션 개발·배포용 플랫폼과 런타임·라이브러리를 제공합니다. 예: IoT 플랫폼, 관리형 ML 플랫폼
> - **SaaS (Software as a Service)**: 완성된 소프트웨어를 바로 사용합니다. 설치·관리가 필요 없습니다. 예: 영양 분석 API, 의료 데이터 분석 서비스

SaaS는 단가가 높은 경우가 많습니다. 반대로 자기 서비스를 SaaS로 만들어 클라우드에 올리면 자동 과금·글로벌 배포가 쉬워진다는 이점이 있습니다. 본편 Part 8에서 만든 AI 서빙 서버를 대외에 공개 API로 내면 그 순간 작은 SaaS가 됩니다.

## 4. 배포 모델 - 클라우드·하이브리드·온프레미스

> [!note] 배포 모델 3 가지
> - **퍼블릭 클라우드**: AWS 같은 공용 클라우드에 전체 배포
> - **온프레미스 (프라이빗 클라우드)**: 사내 데이터 센터에 프라이빗 클라우드 구성. AWS는 특정 기업 전용 프라이빗 구축도 지원합니다
> - **하이브리드**: 일부는 프라이빗, 일부는 퍼블릭으로 혼용

프라이빗이 필요한 전형적 사례는 공공기관의 민감 데이터입니다. 예를 들어 대학 학사·성적 정보처럼 규제상 원본·백업을 물리적으로 떨어진 지역에 분산 보관해야 하는 데이터는 완전 퍼블릭으로 이전하지 못하고 하이브리드로 설계합니다.

## 5. AWS 서비스와 전통 IT 개념의 대응

전통 IT 인프라 개념과 AWS 서비스의 대응을 표로 정리하면 AWS 전체 그림이 한 번에 잡힙니다.

| 전통 IT | AWS 서비스 | 역할 |
|---|---|---|
| 디스크 (블록 스토리지) | Amazon EBS | EC2 인스턴스에 붙이는 블록 볼륨 |
| 파일 시스템 | Amazon EFS | 공유 파일 시스템 |
| 오브젝트 스토리지 | Amazon S3 | 블록·오브젝트 스토리지 |
| RDBMS | Amazon RDS | 관리형 관계형 DB |
| 온프레미스 서버 | Amazon EC2 | 가상 머신 |
| 서버 템플릿 | AMI (Amazon Machine Image) | EC2 인스턴스 생성용 템플릿 |
| 라우터·스위치·VLAN | Amazon VPC, Elastic Load Balancing | 가상 네트워크 |
| 방화벽 | 보안 그룹 (Security Group) | 인스턴스 단위 방화벽 |
| 네트워크 ACL | NACL | 서브넷 단위 방화벽 |
| 관리자·권한 | IAM (Identity and Access Management) | 사용자·역할·권한 관리 |

> [!info] AMI (Amazon Machine Image)
> CPU, 메모리, OS, 설치 소프트웨어 같은 정보를 미리 정의해 둔 템플릿입니다. 하나의 AMI 로부터 동일 스펙의 EC2 인스턴스를 여러 개 찍어낼 수 있습니다.

AWS를 제대로 배운다는 것은 결국 IT 인프라 전반 - 서버, 스토리지, DB, 네트워킹, 보안 - 을 모두 배우는 것과 같습니다.

## 6. 클라우드 컴퓨팅의 6 가지 이점

AWS가 공식적으로 강조하는 이점은 여섯 개입니다.

> [!note] 클라우드 컴퓨팅의 6 가지 이점
> 1. 자본 비용을 가변 비용으로 대체
> 2. 거대한 규모의 경제 혜택
> 3. 용량 추정이 불필요
> 4. 속도와 민첩성 향상
> 5. 데이터 센터 운영·유지 관리 투자 불필요
> 6. 수 분 만에 전 세계 배포

### 6.1 자본 비용 -> 가변 비용

예측 기반 대규모 선투자 대신 실제 사용량에 비례해 지불합니다. 다만 조직의 회계 체계가 "연간 예산 일괄 집행" 구조라면 사용량 기반 과금 자체가 예산 편성에서 낯설게 느껴질 수 있다는 점이 실무 도입의 허들이 되기도 합니다.

### 6.2 규모의 경제

AWS는 전체 고객 사용량을 모아 규모의 경제를 실현하고, 그 절감액을 요금 인하로 돌려준다고 공식 블로그·공지를 통해 밝혀 왔습니다. 2006년 서비스 개시 이후 수십 차례의 요금 인하가 있었습니다.

### 6.3 용량 추정 불필요, 오토 스케일링

> [!example] 과대 추정 vs 과소 추정
> - 전통 환경: 과대 추정으로 과대 투자하거나, 과소 추정으로 피크에 장애
> - 클라우드: 온디맨드 조정으로 실사용 패턴에 맞춰 자동 확장·축소

### 6.4 속도·민첩성

전통 방식은 하드웨어 주문 -> 배송 -> 설치까지 수 주가 걸립니다. 클라우드는 콘솔에서 수 분 내 완료됩니다.

### 6.5 운영 부담 제거

데이터 센터에는 인건비, 유틸리티, 유지관리, 조경, 토지 임대 같은 운영비가 듭니다. 클라우드는 사업 자체와 고객에 투자를 집중할 수 있게 해 줍니다.

### 6.6 글로벌 배포

AWS는 전 세계 다수 리전(Region)을 운영합니다. 리전은 서울, 도쿄, 버지니아 북부(us-east-1), 오레곤 등 지리적으로 독립된 데이터 센터 집합이고, 각 리전 안에는 가용 영역(Availability Zone)이 2 개 이상 있습니다. 클릭 몇 번으로 여러 리전에 서비스를 전개할 수 있습니다. 리전·AZ의 구체 구조는 바로 아래 `8. 글로벌 인프라 3 계층`에서 자세히 살펴봅니다.

## 7. AWS 서비스 범주

AWS는 분석, 애플리케이션 통합, AR·VR·XR, 블록체인, 비즈니스 애플리케이션, 컴퓨팅, 비용 관리, 고객 지원, 게임 기술, IoT, 모바일, 로보틱스, 위성(AWS Ground Station)등 매우 많은 범주의 서비스를 제공합니다.

이 부록에서 집중적으로 다루는 핵심 서비스는 다음과 같습니다.

| 범주 | 주요 서비스 |
|---|---|
| 컴퓨팅 | EC2, Lambda, Elastic Beanstalk, Auto Scaling, ECS, EKS, Fargate |

### 7.1 리전 범위 vs 글로벌 범위

> [!note] 서비스 범위
> 대부분의 서비스는 **리전 범위**로, 해당 리전 안에서만 유효합니다. 예: EC2, Lambda. 일부 서비스는 **글로벌 범위**로 전 세계 공통입니다. 예: IAM, Route 53, CloudFront.

## 8. 글로벌 인프라 3 계층

AWS는 크게 3 단계의 물리·논리 계층으로 인프라를 구성합니다. 각 계층의 경계와 목적이 다르므로 혼동하면 서비스 설계 단계에서 치명적인 실수가 발생합니다.

> [!note] 리전 / 가용 영역 / 엣지 로케이션
> - **리전(Region)**: 지리적 영역. AWS의 최상위 인프라 단위. 서울 리전, 도쿄 리전, 오레곤, 버지니아 같은 단위. 리전끼리는 AWS 자체 백본 전용망으로 이어져 있어 지연이 적습니다
> - **가용 영역(Availability Zone, AZ)**: 리전 안의 물리적으로 격리된 하위 영역. 리전당 일반적으로 2 개 이상입니다. 같은 리전 AZ 끼리는 지연을 최소화하면서도 재해 격리를 위해 수 킬로미터 이상 떨어져 있습니다
> - **엣지 로케이션(Edge Location)**: 리전·AZ와 별도의 콘텐츠 캐시 지점. CloudFront가 사용자 근처에서 콘텐츠를 배달해 지연을 줄이기 위한 POP(Point of Presence) 입니다

### 8.1 리전 간 통신과 전용 백본

리전을 잇는 선은 AWS 전용망입니다. 사용자가 서울 리전과 프랑크푸르트 리전 간 데이터를 복제할 때, 이 전용망 덕에 일반 인터넷 라우팅보다 빠르고 안정적으로 이동합니다.

한편 리전 간 복제는 **자동이 아닙니다**. 사용자가 명시적으로 복제 요청을 해야 하며, 중요한 데이터는 사업 요건에 맞게 2 개 이상의 리전에 백업하는 경우가 많습니다.

### 8.2 AZ가 지리적으로 분산되는 이유

한 리전 내 AZ가 같은 동네에 몰려 있으면 자연 재해 한 번에 전체가 마비됩니다. 국지적 재난을 견디기 위해 AZ는 수 킬로미터 이상 이격되고 자체 전력·네트워크를 가집니다.

> [!info] 데이터 센터는 AZ의 구성 요소
> 하나의 AZ 안에는 여러 개의 데이터 센터가 있고, 한 데이터 센터에는 수만 대의 물리 서버가 들어갑니다. 사용자는 AZ만 선택하고, 그 안의 데이터 센터는 AWS가 자동 배분합니다. 데이터 센터의 정확한 위치는 AWS 내부에서도 필요 기반(need-to-know) 으로만 공유됩니다.

### 8.3 리전 선택의 우선순위

리전을 고를 때 실무적으로 적용하는 우선순위는 다음 네 가지입니다.

1. **법적 요구사항**: 데이터 소재 국가 규제. 예를 들어 특정 국가의 개인정보 관련 법령은 자국 리전 사용을 강제합니다
2. **근접성(지연 시간 최소화)**: 한국 사용자를 대상으로 하는 서비스는 서울 리전이 기본입니다
3. **서비스 가용성**: 최신 인스턴스 타입이 특정 리전에만 먼저 열리는 경우가 있습니다. 필요한 하드웨어가 특정 리전에만 있다면 선택지가 좁아집니다
4. **비용**: 리전별 시간당 단가가 다릅니다. 지연에 민감하지 않으면 저렴한 리전을 선택하는 것도 합리적입니다

### 8.4 엣지 로케이션과 리전 엣지 캐시

CloudFront는 전 세계 사용자에게 콘텐츠를 빠르게 전달하기 위한 CDN 입니다. 이때 사용되는 POP은 다수의 엣지 로케이션과 소수의 리전 엣지 캐시로 구성됩니다.

- **엣지 로케이션**: 자주 액세스되는 콘텐츠를 사용자 근처에 캐싱합니다. 빠른 응답
- **리전 엣지 캐시**: 엣지 로케이션에 상주시킬 만큼 자주 쓰이지는 않지만, 원본 서버까지 가는 것은 피하고 싶은 콘텐츠용 중간 계층

캐시 히트율이 높으면 전체 지연이 크게 줄지만, 잘못 설계하면 오히려 miss 후 원본 조회로 지연이 늘 수 있습니다.

### 8.5 AWS 인프라의 3 대 기능

> [!note] 탄력성·내결함성·고가용성
> - **탄력성(Elasticity)**: 용량을 수요에 맞춰 신속하게 조정합니다. Auto Scaling이 대표적입니다
> - **내결함성(Fault Tolerance)**: 구성요소 장애 시에도 중단 없이 서비스가 지속됩니다. 보조 리소스로 자동 전환하는 방식입니다
> - **고가용성(High Availability)**: 운영 중단을 최소화하고 인적 관리 부담을 낮춥니다

## 9. 솔루션 아키텍처 예시

가장 단순한 AWS 아키텍처 예시의 구성 요소입니다.

```
AWS Cloud
  └── Amazon VPC (가상 격리 네트워크)
        ├── Amazon EC2 (서버 역할)
        ├── Amazon DynamoDB (NoSQL 데이터베이스)
        └── Amazon S3 (오브젝트 스토리지)
```

VPC 안은 **퍼블릭 서브넷** (인터넷 게이트웨이 연결, 외부 접근 허용) 과 **프라이빗 서브넷** (외부에서 들어올 수 없고, 나갈 때만 NAT를 통해 퍼블릭 서브넷 경유) 으로 나뉩니다. 구조는 뒤의 `20. 네트워킹 - VPC와 서브넷`에서 자세히 다룹니다.

### 9.1 Elastic Load Balancing + Auto Scaling

외부 트래픽이 들어오면 Elastic Load Balancer가 여러 EC2 인스턴스에 부하를 분산합니다. 특정 인스턴스가 과부하 상태가 되면 Auto Scaling이 동일 스펙 인스턴스를 복제해 자동 확장하고, 신규 인스턴스도 로드 밸런서에 자동 등록됩니다.

## 11. 요금 모델의 3 가지 기본 요인

> [!note] AWS 요금의 3 대 요소
> 1. **컴퓨팅**: 시간당 또는 초당 청구. 인스턴스 유형(CPU, 메모리, GPU)에 따라 단가가 다릅니다
> 2. **스토리지**: 일반적으로 GB 당 청구
> 3. **데이터 전송**: 아웃바운드는 유료, 인바운드는 기본 무료 (일부 예외 있음)

데이터 전송에서 같은 리전·같은 AZ 내 서비스 간 전송은 무료인 경우가 많지만, 리전 간이나 외부 인터넷으로 나가는 트래픽은 과금됩니다. "무료인 줄 알고 썼는데 청구서가 커졌다" 는 사례는 대부분 이 예외 케이스에서 발생합니다.

## 12. 지불 방식에 따른 할인

> [!note] 예약 인스턴스(Reserved Instance)·Savings Plans의 할인 단계
> - **전체 선결제(All Upfront)**: 가장 높은 할인율
> - **부분 선결제(Partial Upfront)**: 중간 할인율
> - **선결제 없음(No Upfront)**: 약정만으로 일정 할인
> - **온디맨드(예약 없음)**: 기본 단가

구체 할인율은 인스턴스 패밀리·리전·약정 기간(1년·3년)에 따라 다르고, 최대 할인은 60~70% 대까지 올라갑니다. 정확한 수치는 사용 시점의 AWS 공식 요금 페이지 확인을 권장합니다. 또한 S3, EBS, EFS 같은 스토리지 서비스는 **계층화 요금제(tiered pricing)**를 적용해, 사용량이 늘수록 GB 당 단가가 낮아집니다.

> [!warning] 스토리지 계층 선택 주의
> 저빈도 액세스용 저렴한 스토리지(예: S3 Standard-IA, Glacier)에 자주 액세스하는 데이터를 올리면, 요청당 추가 과금이 커져서 오히려 일반 계층보다 비싸질 수 있습니다. 데이터 접근 패턴에 맞춰 스토리지 계층을 고르세요.

## 13. Free Tier와 계정 생성 - 독자 안전 가이드

### 13.1 AWS 계정 만들기 전에 알아둘 것

AWS 계정 가입은 이메일, 신용카드, 전화번호 인증이 필요합니다. Free Tier 범위 안에서만 쓰더라도 "결제 수단 등록이 필수" 라는 점을 유의하세요. AWS 공식 가입 안내에 따르면 한도를 초과하는 순간 즉시 유료 과금으로 전환됩니다.

> [!warning] Free Tier는 "무제한 무료" 가 아닙니다
> Free Tier는 다음 세 가지 유형으로 나뉩니다.
>
> - **12 개월 무료**: 가입 후 1년간 월별 한도 내 무료. 예: EC2 t2.micro·t3.micro 월 750 시간
> - **언제나 무료(Always Free)**: 계정 생존 기간 내내 월별 한도 내 무료. 예: Lambda 월 100만 요청
> - **단기 트라이얼**: 서비스 첫 사용 후 일정 기간만 무료
>
> 구체 한도·서비스 목록은 버전에 따라 바뀌므로 AWS 공식 Free Tier 페이지에서 현재 기준을 확인하세요.

Free Tier에서 자주 확인하는 대표 서비스 예시는 다음과 같습니다. 이 숫자는 외워야 하는 고정 규칙이 아니라, **실습 전에 무료 범위를 다시 확인해야 하는 항목들** 이라고 이해하면 됩니다.

- EC2 t2.micro 또는 t3.micro (리전 조건 충족 시) 월 750 시간
- S3 Standard 5 GB 저장, 요청 횟수 한도
- RDS db.t3.micro 월 750 시간 (MySQL·PostgreSQL·MariaDB 등)
- Lambda 월 100만 요청 + 400,000 GB 초 컴퓨팅 시간 (Always Free)
- DynamoDB 25 GB 저장 + 25 WCU(Write Capacity Unit) + 25 RCU(Read Capacity Unit) 프로비저닝 용량 (Always Free, 월 수억 건 규모의 read/write에 대응)
- VPC, IAM, Elastic Beanstalk, Auto Scaling, CloudFormation 등 자체는 무료(대신 그 안에서 쓰는 EC2·EBS 등이 과금)

### 13.2 실습 안전 5 원칙

본편·부록의 실습을 진행하기 전에 다음 다섯 가지는 반드시 설정해 두기를 권장합니다. AWS 공식 문서에서 반복적으로 권고하는 사항들입니다.

1. **결제 알람(Budgets) 설정**: 월 $1 초과 시 이메일 알림. 과금 실수   를 조기에 포착합니다
2. **Free Tier 사용량 알림 활성화**: 결제 환경설정에서 Free Tier 사용량이 80%·100% 도달 시 자동 알림
3. **MFA(Multi-Factor Authentication)**: 루트 사용자와 생성한 IAM 사용자 모두에 MFA 적용
4. **작업용 IAM 사용자 분리**: 루트 계정으로 직접 실습하지 말고, 권한 범위가 제한된 IAM 사용자로 로그인해 작업
5. **실습 종료 시 리소스 정리**: EC2·Elastic IP·NAT Gateway·RDS·ELB가 가장 큰 비용 요인입니다. 실습 당일 정리를 습관화하세요

> [!warning] 실습 뒤 방치된 리소스는 돈을 태웁니다
> 실습 후 인스턴스를 삭제하지 않고 두어 수 주 뒤에 청구서가 도착하는 사례가 반복적으로 보고됩니다. 작은 t2.micro 라도 Free Tier가 만료된 뒤에는 월 단위로 요금이 누적됩니다. Ch 03 말미의 정리 순서를 반드시 지키세요.

## 14. TCO (Total Cost of Ownership)

> [!note] TCO, 총 소유 비용
> 시스템 도입·운영에 드는 **직접 및 간접 비용**을 합산한 재무 추정입니다. 온프레미스 환경과 AWS 환경을 비교해 클라우드 전환의 비즈니스 사례를 만들 때 사용합니다.

TCO 고려 요소:

| 범주 | 항목 |
|---|---|
| 서버 비용 | 하드웨어, OS·미들웨어 라이선스·업그레이드 |
| 스토리지 비용 | 디스크, 백업 매체 |
| 네트워크 비용 | 회선, 장비 |
| 인건비 | 서버 관리자·운영 인력 |
| 시설 비용 | 공간, 전력, 냉각, 항온항습 |

온프레미스와 비교할 때 **시설 비용(전력·냉각·공간)이 누락** 되는 경우가 많은데, 데이터 센터 규모에서는 이 비용이 상당히 큽니다. AWS는 AWS Pricing Calculator(과거 Simple Monthly Calculator의 후신) 같은 도구로 비용 추정과 온프레미스 대비 절감액 시뮬레이션을 제공합니다.

## 15. AWS Organizations

> [!note] AWS Organizations
> 여러 AWS 계정(Account)을 **계층적으로 묶어 통합 관리** 하는 서비스입니다. 조직 단위(OU, Organizational Unit)로 계정을 그룹화하고, 정책 기반 중앙 관리와 통합 결제를 제공합니다.

### 15.1 주요 기능

- **정책 기반 계정 관리**: 여러 계정에 일관된 보안·거버넌스 정책 적용
- **그룹 기반 권한 관리**: 개발자·운영자 그룹 등 그룹 단위 권한 부여
- **자동화 API**: 계정 생성·정책 적용을 API로 자동화
- **통합 결제 (Consolidated Billing)**: 여러 계정의 비용을 하나의 청구서로 통합

### 15.2 IAM 정책 vs SCP (Service Control Policy)

| 구분 | IAM 정책 | SCP (Service Control Policy) |
|---|---|---|
| 적용 대상 | 사용자·그룹·역할 | 조직 단위(OU) 또는 계정 |
| 역할 | 개별 주체가 어떤 AWS 서비스·액션에 접근 가능한지 | 조직 차원에서 서비스 자체를 허용·차단 |
| 예시 | "이 사용자는 S3 read만 가능" | "이 OU 내 모든 계정은 특정 리전 사용 불가" |

SCP는 IAM 정책의 상위 경계(guardrail) 역할을 합니다. SCP에서 거부한 서비스는 IAM에서 아무리 허용해도 쓸 수 없습니다.

## 16. 결제 대시보드와 비용 모니터링 도구

> [!note] AWS 결제·비용 관리 도구
> - **Billing Dashboard**: 월별 청구 내역, 서비스별 비용 요약
> - **Cost Explorer**: 사용 패턴 시각화, 미래 비용 예측
> - **Budgets**: 예산 임계치 설정 및 알람
> - **Cost and Usage Reports**: 상세 사용 내역 보고서

Cost Explorer는 단순한 청구 조회 도구가 아니라 **사용 패턴 분석 도구** 입니다. 패턴을 파악하면 초기 아키텍처 세팅을 더 효율적으로 조정할 수 있고, 이는 비용 절감과 응답 시간 단축으로 이어집니다.

## 17. 공동 책임 모델

> [!note] AWS Shared Responsibility Model
> 클라우드 보안은 **AWS와 고객이 분담합니다**. AWS가 모든 것을 책임지지도 않고, 고객이 모든 것을 처리하지도 않습니다. 각자가 책임지는 범위를 명확히 이해하지 못하면 보안 구멍이 생깁니다.

### 17.1 AWS 책임 - "Security OF the Cloud"

- 리전·AZ·엣지 로케이션 같은 **물리적 글로벌 인프라**
- **하드웨어와 소프트웨어 인프라** (컴퓨팅, 스토리지, DB, 네트워킹)
- 데이터 센터 **물리적 보안** (위치 비공개, 필요 기반 제어된 액세스)
- **가상화 레이어**와 인스턴스 간 격리
- 하드웨어·스토리지 폐기 절차
- 인프라 수준 침입 탐지와 감사 로깅

### 17.2 고객 책임 - "Security IN the Cloud"

- **데이터 암호화** (클라이언트·서버·전송 중)
- **네트워크 트래픽 무결성**
- **운영체제, 네트워크, 방화벽 구성**
- 플랫폼·애플리케이션·자격 증명·액세스 관리
- **고객 데이터 관리 전반**
- EC2 인스턴스 OS 패치 적용·유지 관리
- 보안 그룹 설정, 호스트 기반 방화벽·IDS·IPS 운영
- 계정·사용자 관리

### 17.3 서비스 모델별 책임 분담

| 모델 | 고객 관리 범위 | AWS 관리 범위 |
|---|---|---|
| IaaS (예: EC2) | OS·네트워크·스토리지 구성, 보안 전반 | 하드웨어·가상화 |
| PaaS (예: RDS, Beanstalk) | 코드·데이터 | 인프라 전체, OS·DB 패치, 백업, 재해 복구 |
| SaaS (예: Amazon Chime) | 구독·사용자 관리 | 인프라·플랫폼·애플리케이션 전체 |

> [!example] 같은 오라클 DB 라도 배치에 따라 책임이 다릅니다
> - **오라클을 EC2에 직접 설치**: 업그레이드·패치·백업은 고객 책임
> - **오라클을 RDS 인스턴스로 실행**: 업그레이드·패치·백업은 AWS 책임
>
> 관리 부담을 줄이고 싶으면 처음부터 RDS를 고르고, 세밀한 커스터마이징이 필요하면 EC2에 직접 설치합니다.

### 17.4 책임 판별 퀴즈

| 시나리오 | 책임 주체 | 이유 |
|---|---|---|
| EC2 인스턴스 OS 업그레이드·패치 | 고객 | IaaS에서 OS는 고객 소유 |
| 데이터 센터 물리 보안 | AWS | 인프라 보안은 AWS 몫 |
| 가상화 인프라 | AWS | 하이퍼바이저 관리 |
| EC2 보안 그룹 설정 | 고객 | 방화벽 규칙은 고객이 설계 |
| EC2 위 애플리케이션 구성 | 고객 | 앱은 고객 소유 |
| RDS 인스턴스의 오라클 패치 | AWS | 관리형 DB 엔진 관리 |
| EC2에 직접 설치한 오라클 패치 | 고객 | 셀프 매니지드 엔진 |
| S3 버킷 액세스 구성 | 고객 | 누가 접근하는지는 고객이 결정 |
| AWS 매니지먼트 콘솔 해킹 차단 | AWS | AWS가 운영하는 웹 |
| VPC 서브넷 구성 | 고객 | 사용자 네트워크 설계 |
| 리전 네트워크 중단 대응 | AWS | 인프라 가용성 |
| SSH 키 보안 | 고객 | 고객이 소유·배포 |
| AZ 간 데이터 격리 보장 | AWS | 인프라 격리 |
| CloudFront와 S3 버킷 저지연 연결 | AWS | 네트워크 보장 |
| MFA 적용 | 고객 | 고객이 선택·활성화 |

## 18. IAM - 자격 증명과 액세스 관리

> [!note] IAM의 역할
> AWS 리소스에 대한 **인증(Authentication)**과 **권한 부여(Authorization)**를 처리합니다. **무료 서비스** 이고 글로벌 범위라 모든 리전에 동시 적용됩니다.

### 18.1 IAM의 4 대 요소

| 요소 | 설명 |
|---|---|
| **User(사용자)** | AWS를 이용하는 사람 또는 애플리케이션. 각자 자격 증명(아이디·패스워드 또는 액세스 키)을 소유합니다 |
| **Group(그룹)** | 사용자 모임. 그룹에 정책을 걸면 소속 사용자 전원에 적용됩니다. 한 사용자가 여러 그룹에 속할 수 있고 그룹 중첩은 불가합니다 |
| **Policy(정책)** | 어떤 리소스에 어떤 작업을 허용·거부할지 정의하는 JSON 문서. 단독으로는 효력이 없고 사용자·그룹·역할에 부착해야 작동합니다 |
| **Role(역할)** | 일시적 권한 집합. 사람이 아니라 애플리케이션·서비스가 수임(assume)합니다. 한정된 기간의 자격 증명을 제공합니다 |

> [!warning] IAM과 AMI 혼동 주의
> - **IAM**: Identity and Access Management. 계정·권한 관리
> - **AMI**: Amazon Machine Image. EC2 OS 이미지
>
> 철자가 비슷해 헷갈리기 쉽습니다. 문맥상 "권한·사용자" 얘기면 IAM, "가상 머신 이미지·OS" 얘기면 AMI 입니다.

### 18.2 액세스 유형

- **프로그래밍 방식 액세스**: CLI 또는 SDK. 액세스 키 ID와 시크릿 액세스 키로 인증
- **AWS 매니지먼트 콘솔 액세스**: 웹 브라우저. 아이디·패스워드
- **MFA(Multi-Factor Authentication)**: 아이디·패스워드에 더해 스마트폰 OTP 코드 요구. Google Authenticator, Microsoft Authenticator 등으로 생성

### 18.3 정책의 종류

- **자격 증명 기반(Identity-based)**: IAM 사용자·그룹·역할에 부착. "이 사용자가 무엇을 할 수 있나"
- **리소스 기반(Resource-based)**: S3 버킷 같은 리소스 자체에 부착. "이 리소스에 누가 접근할 수 있나"

하나의 정책을 여러 엔터티에 부착할 수 있고, 하나의 엔터티에 여러 정책을 부착할 수도 있습니다.

### 18.4 최소 권한 원칙과 평가 순서

> [!note] 최소 권한(Least Privilege)
> 사용자에게 처음부터 많은 권한을 주지 말고, **필요한 최소 권한만 부여** 합니다. 업무 변화에 따라 조금씩 추가합니다.

권한 결정 순서:

1. 어느 정책에서든 **명시적 거부(Explicit Deny)**가 있으면 거부 (가장 강력)
2. **명시적 허용(Explicit Allow)**이 있으면 허용
3. 어느 쪽도 없으면 **암시적 거부(Implicit Deny)** (기본값)

### 18.5 정책 JSON 예시

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "dynamodb:*",
        "s3:*"
      ],
      "Resource": [
        "arn:aws:dynamodb:ap-northeast-2:123456789012:table/MyTable",
        "arn:aws:s3:::my-bucket",
        "arn:aws:s3:::my-bucket/*"
      ]
    },
    {
      "Effect": "Deny",
      "Action": [
        "dynamodb:*",
        "s3:*"
      ],
      "NotResource": [
        "arn:aws:dynamodb:ap-northeast-2:123456789012:table/MyTable",
        "arn:aws:s3:::my-bucket",
        "arn:aws:s3:::my-bucket/*"
      ]
    }
  ]
}
```

해석:

- 특정 DynamoDB 테이블과 S3 버킷에는 모든 DynamoDB·S3 작업 허용
- 그 외의 DynamoDB 테이블·S3 버킷에 대한 모든 작업은 명시적 거부

명시적 거부가 들어 있어, 다른 정책이 허용해도 결과적으로 거부가 이깁니다.

### 18.6 역할(Role) 활용 패턴

> [!example] EC2 애플리케이션이 S3에 접근하는 시나리오
> 1. S3 버킷 액세스를 허용하는 **정책을 생성** 합니다
> 2. 이 정책을 **역할에 연결** 합니다
> 3. 역할을 **EC2 인스턴스에 부여** 합니다
> 4. EC2 위 애플리케이션은 코드에 자격 증명을 하드코딩하지 않고도 S3에 접근할 수 있습니다
>
> 액세스 키를 코드에 심지 않아도 되므로 보안·배포 면에서 훨씬 깔끔합니다.

### 18.7 IAM 콘솔 실습 흐름 요약

콘솔에서 IAM을 다룰 때의 표준 조작 순서입니다.

1. **Role 생성**: IAM -> Roles -> Create role
    - Trusted entity로 EC2 선택
    - Amazon S3 ReadOnlyAccess, DynamoDB ReadOnlyAccess 정책 부착
    - 이름(예: MyAppRole) 지정 후 생성
2. **EC2 Launch 시 Role 지정**: 인스턴스 생성 중 IAM role 드롭다운에서 MyAppRole 선택
3. **Group 생성**: NetOps 그룹 생성 후 AmazonVPCFullAccess 정책 부착
4. **User 생성**: 사용자(예: Dave) 생성, 콘솔 액세스 허용, 최초 로그인 시 비밀번호 변경 요구, NetOps 그룹에 추가
    - 그룹 멤버십을 통해 VPC Full Access 상속
5. **커스텀 정책 작성**: Policies -> Create policy -> Visual editor 또는 JSON 직접 작성

## 19. 계정 보안 강화

### 19.1 루트 사용자 사용 제한

> [!warning] 루트 계정은 꼭 필요할 때만 사용
> 루트 사용자는 모든 리소스에 무제한 접근합니다. 일상적 작업에는 절대 쓰지 마세요.

루트 계정이 꼭 필요한 작업은 다음과 같습니다.

- 계정 암호 업데이트
- AWS Support 플랜 변경
- IAM 사용자 권한 복원
- 계정 설정 변경(연락처, 결제 수단 등)

그 외에는 다음 절차로 루트 사용을 중단합니다.

1. 루트로 로그인한 상태에서 자신용 IAM 사용자를 생성하고, 필요한 액세스 키를 저장합니다
2. IAM 그룹을 생성해 전체 관리자 권한을 부여하고, 자신을 그 그룹에 추가합니다
3. 루트 계정의 액세스 키를 비활성화·제거합니다
4. 사용자 계정에 암호 정책을 활성화합니다
5. 이후에는 IAM 사용자 자격 증명으로만 로그인합니다
6. 루트 자격 증명은 안전한 장소에 보관합니다

### 19.2 MFA 활성화

- **루트 사용자와 모든 IAM 사용자** 에게 MFA 적용을 권장합니다
- 가상 MFA: Google Authenticator, Microsoft Authenticator 같은 앱이 6 자리 OTP를 생성합니다
- 하드웨어 MFA 키(YubiKey 등)도 지원합니다

### 19.3 CloudTrail로 활동 추적

- 계정의 **모든 API 호출을 로그로 남깁니다**
- 기본적으로 활성화되어 있고, 최근 90 일 이벤트 히스토리는 무료로 제공됩니다
- 90 일 이상 보존하려면 Trail을 생성해 S3 버킷에 저장 (S3 비용이 발생합니다)
- 비정상 활동 탐지·감사용으로 필수입니다

### 19.4 결제 보고서

- 리소스 사용 내역과 추정 비용을 S3 버킷으로 전송할 수 있습니다
- 하루 1 회 이상 업데이트됩니다
- Budgets와 연동해 예산 초과 시 알림을 받을 수 있습니다

## 20. 네트워킹 - VPC와 서브넷

### 20.1 IP 주소 기초

- **IPv4**: 32 비트. 4 개 10 진수(0~255)를 점으로 구분합니다. 예: `192.0.2.0`. 각 숫자는 8 비트
- **IPv6**: 128 비트. 16 비트 16 진수 8 그룹. 예: `2001:0db8:85a3:0000:0000:8a2e:0370:7334`
- **CIDR 표기**: `192.0.2.0/24`는 앞 24 비트가 고정, 뒤 8 비트만 호스트용. 즉 256 개 주소

> [!info] OSI 7 계층 참고
> 물리 - 데이터 링크 - 네트워크 - 전송 - 세션 - 표현 - 응용. AWS의 네트워킹 서비스도 이 모델을 따릅니다. VPC 통신을 이해할 때 어느 계층에서 무슨 일이 일어나는지 구별하면 설계가 쉬워집니다.

### 20.2 VPC(Virtual Private Cloud)

> [!note] VPC 란
> AWS 클라우드의 **논리적으로 분할된 사용자 소유 네트워크 영역** 입니다. 리전 내에 만들고, 여러 AZ에 걸쳐 존재할 수 있습니다. IP 주소 범위, 서브넷, 라우팅 테이블, 게이트웨이 등을 사용자가 직접 구성합니다.

VPC는 **리전 범위** 리소스입니다. 가용 영역보다 상위 개념이며, 여러 AZ를 포괄합니다.

### 20.3 서브넷(Subnet)

- VPC 안을 다시 논리적으로 쪼갠 단위입니다
- 서브넷은 **반드시 단일 AZ에 속합니다**. AZ 경계를 넘지 못합니다
- 용도별로 **퍼블릭 서브넷**과 **프라이빗 서브넷**으로 나눕니다

구성 예:

```
Region (ap-northeast-2: 서울)
└── VPC (10.0.0.0/16)
    ├── AZ-a
    │   ├── 퍼블릭 서브넷 (10.0.1.0/24) -> 웹 서버
    │   └── 프라이빗 서브넷 (10.0.2.0/24) -> DB
    └── AZ-c
        ├── 퍼블릭 서브넷 (10.0.3.0/24) -> 웹 서버 복제
        └── 프라이빗 서브넷 (10.0.4.0/24) -> DB 복제
```

가용 영역 2 개에 각각 퍼블릭·프라이빗 서브넷을 두면 한 AZ 장애에도 서비스가 유지됩니다.

> [!info] VPC CIDR 블록 크기 제한
> - 최대: /16 (65,536 개 주소)
> - 최소: /28 (16 개 주소)
>
> VPC 생성 후에는 CIDR 블록을 변경할 수 없으니 초기 설계가 중요합니다.

### 20.4 퍼블릭 서브넷의 라우팅

퍼블릭 서브넷은 인터넷과 직접 통신할 수 있도록 구성합니다.

1. **인터넷 게이트웨이(IGW)**를 VPC에 부착합니다
2. 퍼블릭 서브넷의 **라우팅 테이블**에 기본 경로 `0.0.0.0/0 -> IGW`를 추가합니다
3. 해당 서브넷의 인스턴스에 퍼블릭 IP를 할당합니다

이 세 조건이 모두 갖춰져야 외부에서 웹 서버에 접속할 수 있습니다.

### 20.5 프라이빗 서브넷과 NAT 게이트웨이

프라이빗 서브넷은 인터넷에서 **직접 접근할 수 없습니다**. 다만 프라이빗 내 인스턴스가 외부(예: 패치 다운로드)에 **아웃바운드로 나가는 것**은 허용하고 싶을 때가 많습니다.

해결책은 **NAT 게이트웨이** 입니다.

1. 퍼블릭 서브넷에 NAT 게이트웨이를 배치합니다
2. 프라이빗 서브넷의 라우팅 테이블에 `0.0.0.0/0 -> NAT GW`를 추가합니다
3. 프라이빗 인스턴스는 NAT GW를 거쳐 IGW로 나가 인터넷에 접속합니다
4. 외부에서 프라이빗으로 직접 들어오는 경로는 여전히 없습니다

> [!example] 3-tier 웹 아키텍처 네트워크 설계
> - **웹 서버**: 퍼블릭 서브넷. 외부 사용자 브라우저가 HTTPS로 접근
> - **애플리케이션 서버·DB**: 프라이빗 서브넷. 웹 서버만 접근 가능
> - **DB 패치**: 프라이빗 서버가 NAT 게이트웨이를 통해 외부 리포지토리에서 다운로드
>
> 이렇게 하면 DB가 인터넷에 직접 노출되지 않아 공격 표면이 크게 줄어듭니다.

### 20.6 VPC 간 연결 옵션

- **VPC Peering**: 두 VPC 간 1:1 프라이빗 연결. 동일 계정·다른 계정·다른 리전 모두 가능
- **Transit Gateway**: 여러 VPC와 온프레미스를 허브로 묶는 방식. 대규모 네트워크에 적합
- **VPN**: 공용망 위에 암호화 터널. 온프레미스 -> AWS
- **Direct Connect**: 전용 프라이빗 회선. 대역폭·저지연·저비용

### 20.7 보안 그룹과 NACL

| 구분 | 보안 그룹 (Security Group) | NACL (Network ACL) |
|---|---|---|
| 적용 단위 | 인스턴스(ENI) | 서브넷 |
| 상태 | stateful (반환 트래픽 자동 허용) | stateless (양방향 규칙 별도) |
| 규칙 | allow만 | allow·deny 모두 |
| 기본값 | 인바운드 거부, 아웃바운드 허용 | 인바운드·아웃바운드 모두 허용 |

실무에서는 주로 보안 그룹으로 세밀한 접근 제어를 하고, NACL은 서브넷 단위의 굵은 거부 정책에 사용합니다.

## 21. 서비스 범위 정리

Ch 02·03 실습에 앞서, 다루는 서비스의 범주와 범위를 한 번 정리하고 갑니다.

| 서비스 | 범주 | 범위 |
|---|---|---|
| IAM | 보안·자격증명·규정 | 글로벌 |
| Route 53 | 네트워킹·콘텐츠 전송 | 글로벌 |
| CloudFront | 네트워킹·콘텐츠 전송 | 글로벌 |
| EC2 | 컴퓨팅 | 리전 |
| Lambda | 컴퓨팅 | 리전 |
| S3 | 스토리지 | 리전(버킷 이름은 글로벌 고유) |
| VPC | 네트워킹 | 리전(VPC 자체) |
| 서브넷 | 네트워킹 | 가용 영역 |
| EBS | 스토리지 | 가용 영역 |

"왜 이 서비스를 쓸 때 리전을 먼저 고르게 하는가" 에 대한 답이 여기에 있습니다. 리전 범위 서비스는 선택한 리전 안에서만 유효하고, 그 리전을 벗어나면 다시 만들어야 합니다.

## 22. AWS 자격증 트랙 개요

AWS 공식 자격증 트랙은 크게 네 단계입니다.

- **Foundational - Cloud Practitioner(CLF)**: 가장 기초. 클라우드 개념·AWS 핵심 서비스 전반
- **Associate - Solutions Architect·Developer·SysOps Administrator**: 중급. 각 직무별로 분리
- **Professional - Solutions Architect Professional·DevOps Engineer Professional**: 고급
- **Specialty - Security·Machine Learning·Data Analytics·Advanced Networking 등**: 전문 영역

이 부록의 3 개 챕터는 Cloud Practitioner의 핵심 개념 범위와 상당 부분 겹칩니다. 부록을 완독한 뒤 Cloud Practitioner 시험을 준비하면 개념 복습으로 자연스럽게 이어집니다.

## 23. 마무리

이 챕터는 AWS를 다루는 모든 작업의 공통 바닥을 깔았습니다.

- 클라우드의 본질은 온디맨드·사용량 기반 과금이고, 그 위에 IaaS·PaaS·SaaS가 쌓여 있습니다
- AWS 물리·논리 인프라는 리전 -> 가용 영역 -> 엣지 로케이션 3 계층입니다
- 요금은 컴퓨팅·스토리지·데이터 전송의 3 요소에서 나오며, 예약·Savings Plans·Free Tier로 비용을 낮춥니다
- 보안은 공동 책임 모델로 AWS와 고객이 역할을 나눕니다
- IAM 4 요소(User·Group·Policy·Role), 최소 권한 원칙, MFA가 계정 보안의 기본입니다
- VPC·서브넷·라우팅·NAT·보안 그룹이 네트워크 설계의 기초입니다

다음 Ch 02 에서는 이 위에 **스토리지와 데이터베이스**를 얹습니다. EBS·S3·EFS·Glacier·RDS·Aurora·DynamoDB·Redshift를 각자의 사용처와 비용 구조로 구분해 고를 수 있게 하는 것이 목표입니다. Ch 03 에서는 **컴퓨팅·서버리스**로 EC2·Cloud9·Lambda를 엮어 실제 파이프라인을 만듭니다.
