# 02. 규칙기반 전문가 시스템과 퍼지 추론

> 앞 챕터에서 본 기호주의 세계관의 가장 오래되고 직관적인 구체 기법이 **규칙기반 전문가 시스템**입니다. 사람이 알고 있는 규칙을 코드로 명시하고, 추론 엔진이 그 규칙을 조합해 결론을 끌어냅니다. 이어서 이분 논리의 경직성을 완화한 **퍼지 이론**을 짧게 살펴봅니다.

## 1. 전문가 시스템이 필요했던 맥락

AI를 사람의 판단을 돕는 시스템으로 만들려는 수요가 본격적으로 커진 것은 1970년대 전후입니다. 이 무렵 인간-컴퓨터 상호작용(HCI)과 이후의 인간-로봇 상호작용(HRI) 같은 연구 흐름도 함께 발전했고, 그 해답 중 한 갈래가 **전문가의 지식을 규칙으로 옮겨 담은 시스템**이었습니다.

1970~1980년대에는 인간 전문가의 지식을 디지털 시스템으로 옮겨 두고 싶은 수요가 특히 강했습니다. 의사의 감염 진단, 광물 탐사, 설비 고장 진단 같은 도메인은 경험 많은 소수의 전문가에게 크게 의존했고, 이들의 판단을 규칙으로 풀어 저장해 두면 여러 현장에서 재사용할 수 있었습니다.

Stanford의 MYCIN(1970년대 초반, 감염 진단)과 DENDRAL(화학 구조 식별) 같은 초기 시스템이 이 흐름의 대표 사례였고, 이 접근을 일반화한 소프트웨어 형태가 **전문가 시스템(Expert System)**입니다.

## 2. 지식을 규칙으로 표현하기

전문가 시스템의 가장 흔한 지식 표현 방식은 **IF-THEN 규칙** 입니다. "IF 조건이 성립하면 THEN 어떤 결론이나 행동을 취한다" 라는 단순한 구조지만, 여러 규칙이 연쇄적으로 작동하면 상당히 복잡한 추론도 표현할 수 있습니다.

```text
규칙 R1: IF  열이 있다 AND 기침이 있다
         THEN 감기 의심

규칙 R2: IF  감기 의심 AND 목이 붓지 않았다
         THEN 일반 감기

규칙 R3: IF  감기 의심 AND 목이 붓다
         THEN 편도염 의심
```

이때 "열이 있다", "기침이 있다" 같은 참/거짓 단언을 **팩트(fact)** 라 하고, IF-THEN 문장을 **룰(rule)** 이라 합니다. 지금 알려진 팩트의 모음을 **작업 메모리(Working Memory)** 라 부릅니다.

IF-THEN 외에도 **시멘틱 네트워크**·**프레임(Frame)**·**스크립트(Script)**·**온톨로지** 등 다양한 지식 표현 기법이 있습니다. 전문가 시스템은 이들 중에서도 규칙과 구조화된 지식에 무게를 둔 접근입니다. 넓게 보면 지식 표현은 "**사람이 이해하기 쉬운 형태** (자연어·시각언어)" 에서 "**기계가 다루기 쉬운 형태** (기호·규칙·통계 모델·신경망)" 까지의 스펙트럼 위에 놓여 있습니다. 왼쪽으로 갈수록 표현력은 풍부하지만 기계가 그대로 쓰기 어렵고, 오른쪽으로 갈수록 기계가 바로 처리할 수 있는 대신 사람의 직관을 잃기 쉽습니다.

현대 시스템에서 가장 자주 재발견되는 지식 표현은 **규칙**과 **그래프(트리플)**입니다. 예컨대 `(카나리아, isA, 새)`, `(새, canDo, 날다)` 같은 `(주어, 관계, 목적어)` 3원 형태를 **트리플(Triple)**이라 하며, Google Knowledge Graph·Wikidata가 이를 대규모로 축적해 검색 엔진·음성 비서 답변에 활용하고 있습니다. 이 챕터는 지식 표현 중 **규칙** 쪽에 집중하고, 그래프 기반 표현은 Part 2 Ch 01에서 소개한 수준에서 일단 마무리합니다.

## 3. 규칙기반 전문가 시스템의 구조

전형적인 규칙기반 전문가 시스템은 다섯 개의 구성 요소로 나뉩니다.

| 구성 요소 | 역할 |
|---|---|
| Knowledge Base | 도메인 지식을 IF-THEN 규칙 형태로 저장 |
| Working Memory | 지금까지 알려진 팩트를 담는 작업 메모리 |
| Inference Engine | 규칙과 팩트를 조합해 새 결론을 도출하는 엔진 |
| Explanation Facility | "왜 이 결론인가"를 역추적해 보여 주는 설명 기능 |
| User Interface | 사용자로부터 팩트를 입력받고 결과를 전달하는 UI |

Knowledge Base와 Inference Engine의 **분리**가 이 설계의 핵심입니다. 도메인이 바뀌어도 Inference Engine은 그대로 두고 Knowledge Base만 교체하면 되므로, 의료·금융·제조 등으로 범용 재사용이 가능했습니다.

## 4. 추론 전략 - 순방향과 역방향

Inference Engine이 규칙을 적용하는 두 가지 대표 방향이 있습니다.

### 4.1 순방향 연결 (Forward Chaining)

알려진 팩트로부터 시작해 **적용 가능한 규칙**을 찾아 새 팩트를 만들어 나갑니다. "주어진 증상으로부터 가능한 진단을 쌓아간다"는 접근입니다.

```text
초기 팩트: {열, 기침}
R1 적용 -> 팩트 추가: {열, 기침, 감기 의심}
R2 또는 R3 적용 -> 추가 사용자 질의("목이 붓는가?") 이후 결론 확정
```

데이터 중심·탐색적 진단에 잘 맞습니다.

### 4.2 역방향 연결 (Backward Chaining)

**가설(결론)**에서 시작해 그 결론을 성립시킬 조건을 역추적합니다. "편도염인지 확인하려면 어떤 증상이 필요한가"를 되짚어 올라가는 접근입니다. 사용자에게 묻는 질문이 가설 중심으로 한정되어 대화가 자연스럽게 흐르는 장점이 있어, 대화형 진단 시스템에 자주 쓰였습니다.

## 5. 규칙 충돌과 충돌 해법

작업 메모리 상태에 따라 **여러 규칙이 동시에 적용 가능** 한 순간이 생기기 마련입니다. 이때 어느 규칙을 먼저 적용할지 정하는 전략을 **충돌 해법(Conflict Resolution)** 이라 부르며, 대표적인 방식은 다음과 같습니다.

- **규칙 우선순위**: 규칙마다 중요도를 미리 부여
- **가장 구체적인 규칙 우선 (Specificity)**: 조건 수가 많은 규칙을 먼저 적용
- **가장 최근 팩트 기반 규칙 우선 (Recency)**: 최근 업데이트된 팩트와 관련된 규칙 우선
- **규칙 발동 1회 제한 (Refractoriness)**: 같은 팩트 조합으로 한 번 발동된 규칙은 재발동 제외

충돌 해법은 규칙 수가 수십~수백 개 규모로 커질 때 시스템 일관성을 유지하는 장치입니다.

## 6. 미니 예제 - 파이썬으로 본 순방향 추론

전용 도구도 있지만, 여기서는 개념 이해를 위해 파이썬 표준 문법으로 순방향 연결 엔진을 가볍게 구현해 봅니다. CLIPS·Drools·`experta` 같은 도구는 같은 아이디어를 더 큰 시스템에 적용할 때 자주 쓰입니다.

```python
# 팩트는 문자열 집합, 규칙은 (조건 집합, 결론) 튜플
rules = [
    ({"열", "기침"}, "감기 의심"),
    ({"감기 의심", "목 부음"}, "편도염 의심"),
    ({"감기 의심", "목 정상"}, "일반 감기"),
]

def forward_chain(initial_facts, rules):
    facts = set(initial_facts)
    changed = True
    while changed:
        changed = False
        for conditions, conclusion in rules:
            # set 간 `<=`는 부분집합 검사: 조건이 모두 팩트에 있는가
            if conditions <= facts and conclusion not in facts:
                facts.add(conclusion)
                changed = True
    return facts

forward_chain({"열", "기침", "목 부음"}, rules)
# {'열', '기침', '목 부음', '감기 의심', '편도염 의심'}
```

규칙은 데이터(리스트)로, 추론은 단순 루프 하나로 표현됩니다. 규칙을 교체하면 동일 엔진으로 다른 도메인 진단을 구동할 수 있다는 것이 Knowledge Base와 Inference Engine 분리의 효과입니다.

## 7. 규칙기반 시스템의 한계

규칙기반 접근에는 뚜렷한 한계가 있습니다.

- **규칙 수 폭발**: 도메인이 복잡해질수록 규칙이 수천 개로 늘어나고 상호 충돌을 관리하기 어려워집니다.
- **이분 논리의 경직성**: IF-THEN은 "열이 있다 / 없다" 같은 이분법에 의존합니다. "열이 **약간** 있다" 같은 연속적인 상태를 자연스럽게 담지 못합니다.
- **예외와 새 상황에 약함**: 규칙에 없는 상황이 들어오면 시스템이 침묵하거나 엉뚱한 답을 줍니다.
- **지식 획득 병목**: 전문가의 암묵지를 규칙으로 옮기는 작업 자체가 대단히 비쌉니다.

특히 "연속성을 다루지 못한다" 는 약점을 수학적으로 보완한 것이 **퍼지 이론** 입니다.

## 8. 퍼지 이론 - 0과 1 사이의 진리값

1965년 Lotfi Zadeh가 제안한 **퍼지 집합(Fuzzy Set)**은 원소가 집합에 속하는 정도를 `[0, 1]` 구간의 연속값(**소속도, membership degree**)으로 표현합니다. 전통 집합이 "속한다(1) / 속하지 않는다(0)" 이분법인 것과 대비됩니다.

예컨대 "젊다" 라는 개념은 명확한 경계가 없습니다. 퍼지 집합에서는 "젊다" 를 나이에 따라 부드럽게 변하는 곡선으로 표현합니다.

```python
import numpy as np

def young(age):
    """'젊다'에 대한 간단한 삼각형 소속 함수
    - 25세 이하: 소속도 1.0
    - 25~40세: 선형으로 1.0에서 0.0까지 감소
    - 40세 이상: 소속도 0.0
    """
    if age <= 25:
        return 1.0
    elif age <= 40:
        return (40 - age) / 15
    else:
        return 0.0

[young(a) for a in [20, 28, 35, 40, 50]]
# [1.0, 0.8, 0.333..., 0.0, 0.0]
```

이 "젊다의 정도"가 0 또는 1 대신 소수점이라는 점이 퍼지 논리의 출발점입니다. 한 사람이 "젊다"에 0.8, 동시에 "중년이다"에 0.2의 소속도를 가질 수 있습니다.

## 9. 맘다니(Mamdani) 퍼지 추론

퍼지 논리를 실제 제어에 쓰기 위해 1975년 Ebrahim Mamdani가 제안한 추론 방식이 현재까지 퍼지 제어의 표준으로 자리 잡았습니다. 과정은 세 단계입니다.

1. **Fuzzification (퍼지화)**: 입력값을 각 퍼지 집합에 대한 소속도로 변환. 예: 온도 `28도` -> `{춥다: 0.0, 적당: 0.7, 덥다: 0.3}`
2. **Rule Inference (규칙 추론)**: IF-THEN 퍼지 규칙을 적용해 출력 퍼지 집합의 소속도를 계산. 여러 규칙의 결과는 보통 `max` 등으로 결합
3. **Defuzzification (역퍼지화)**: 출력 퍼지 집합을 다시 단일 수치로 환원. **무게중심(Center of Gravity)** 방식이 가장 흔합니다

IF-THEN 구조는 규칙기반 시스템과 같지만, 조건과 결론이 **소속도라는 연속값**을 타고 흐른다는 점이 핵심 차이입니다.

간단한 에어컨 제어를 상상해 보겠습니다. 입력은 실내 온도 하나, 출력은 냉방 세기 하나로 단순화합니다. 규칙이 다음과 같이 세 개 있다고 할 때,

```text
R1: IF 온도 == 덥다   THEN 냉방 강
R2: IF 온도 == 적당   THEN 냉방 약
R3: IF 온도 == 춥다   THEN 냉방 끔
```

실내 온도가 `28도`라면 퍼지화 결과가 `{춥다: 0.0, 적당: 0.7, 덥다: 0.3}` 정도로 나옵니다. 따라서 `적당`에 해당하는 R2는 0.7의 강도로, `덥다`에 해당하는 R1은 0.3의 강도로 활성화되고, `춥다`에 해당하는 R3는 활성화되지 않습니다. 이렇게 얻은 출력 퍼지 집합을 합친 뒤 무게중심으로 역퍼지화하면 "냉방 세기 = 약 40%" 같은 단일 수치가 나옵니다. 여러 규칙이 서로 다른 정도로 동시에 기여하면서도 결과는 연속적이고 부드러운 값이 된다는 점이 맘다니 추론의 특징입니다.

## 10. 퍼지 제어의 실제 응용

실제 제품에서는 맘다니의 전체 추론을 매번 계산하기보다, 결과를 표로 미리 정리해 두고 꺼내 쓰는 경우가 많습니다. 이 단순화된 형태가 **제어 규칙표(Control Rule Table)**입니다. 편차 `e = 측정값 - 기댓값`과 편차 변화량 `Δe`를 행·열로 두고, 각 칸에 미리 계산한 출력 값을 적어 둡니다. 예를 들어 PB는 양의 큰 값, NS는 음의 작은 값, ZO는 0 근방을 뜻합니다. 이렇게 하면 복잡한 추론 대신 표를 한 번 조회하는 것만으로 응답할 수 있어, 저사양 마이크로컨트롤러에서도 부드러운 제어가 가능합니다.

퍼지 제어는 규칙이 단순하면서도 연속적 제어가 필요한 소비자 전자와 산업 현장에서 오래 살아남았습니다.

- **세탁기·에어컨**: 빨래량·수질·실내외 온도차에 따라 세척·냉방 강도를 부드럽게 조절
- **카메라 자동초점**: 피사체 거리와 움직임에 따라 연속적 초점 보정
- **자동차 엔진·ABS 브레이크**: 제동력·연료 분사량의 미세 조정
- **지하철 제어 (1987년 일본 센다이)**: 퍼지 제어가 대규모 상용에 성공한 초창기 사례로 자주 인용

이런 응용에서 퍼지 제어는 "모델을 정확히 수식화하기 어려운 시스템을 몇 개 규칙으로 합리적으로 제어" 하는 실용적 도구 역할을 해 왔습니다.

## 마무리

규칙기반 전문가 시스템과 퍼지 추론은 기호주의가 실제 엔지니어링으로 이어진 대표 사례입니다. 오늘날 실무의 중심은 연결주의·딥러닝으로 옮겨 갔지만, 도메인 지식을 명시적으로 담고 판단 근거를 설명해야 하는 분야에서는 규칙 기반 접근이 여전히 중요합니다. 의료·법률·안전 규제 시스템이 대표적입니다.

다음 챕터에서는 기호주의의 또 다른 줄기인 **탐색 기반 AI**로 넘어갑니다. 상태 공간과 휴리스틱이라는 개념으로 "문제를 푸는 또 하나의 방식"을 살펴봅니다.
