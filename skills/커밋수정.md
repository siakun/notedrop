## 0. 에이전트 호출 프로토콜

### 0.1 호출 예시

다음 중 하나처럼 호출되면 즉시 실행:

- `"커밋 abc1234 메시지를 'docs: foo' -> '✨ feat: foo'로 바꿔"`
- `"최근 5개 커밋 메시지에서 ·를 모두 ,로 교체"`
- `"HEAD 커밋 body에 'BREAKING:' 줄 추가"`
- `"@커밋수정.md 적용해서 8c43f88 메시지를 새 컨벤션으로 다시 써"`

### 0.2 호출 시 즉시 확인할 것

1. 수정 대상 commit SHA(들) 식별 — 사용자가 SHA를 줬으면 그대로, 안 줬으면 `git log` 로 후보 보여주고 확인 받기
2. 수정 범위가 원격에 push 된 커밋인지 확인 (`git log origin/main..HEAD` / `git log HEAD..origin/main`)
3. push 된 커밋 수정 시 force-push 필요 -> 사용자 명시 승인 후에만 진행

### 0.3 절대 금지

- `git rebase -i` (interactive 플래그 금지 — 환경 제약)
- `git push --force` (반드시 `--force-with-lease`)
- `--no-verify`, `--no-gpg-sign` (hook·서명 우회 금지)
- bundle 백업 생성 전 어떤 rewrite도 시작하지 않음
- 사용자 승인 없는 main reset / force-push
- 검증 단계 건너뛰기

```
[현재 상태] main 또는 작업 브랜치
    |
    v
1. bundle 파일 백업  (영구 롤백 보험)
    |
    v
2. edit 브랜치 분리  (main 무손상)
    |
    v
3. 편집 수행  (도구는 §4 에서 선택)
    |
    v
4. 검증  (range-diff + 트리 동일성)
    |
    v
5. 사용자 보고 + 적용 승인 받기
    |
    v
6. main 적용 (필요시 force-push) + bundle 파일 보존
```

각 단계 출력은 다음 단계 입력. 한 단계 실패하면 즉시 중단하고 사용자에게 알림.

## 2. 사전 점검

수정 시작 전 반드시 확인:

```bash
# 작업 디렉토리가 깨끗한지
git status

# 현재 브랜치
git branch --show-current

# 수정 대상 커밋이 origin 에 push 됐는지
git branch -r --contains <SHA>

# 수정 대상 커밋의 현재 상태 (원본 보존용)
git show --no-patch --format='%H%n%an <%ae>%n%aI%n%cI%n%s%n%n%b' <SHA>
```

확인 결과 사용자에게 보고:

```
- 대상 SHA: <SHA>
- 작성자: <author>
- 작성 시각: <author date>
- 커밋 시각: <committer date>
- 현재 메시지: <subject>
- push 상태: pushed to origin/main / local only
```

작업 디렉토리가 더러우면 `git stash` 또는 commit 먼저 하라고 안내. 임의로 stash 하지 않음.

## 3. 백업 + 작업 공간

### 3.1 백업 (bundle 파일 전용)

**v1.0 결함:** annotated tag 는 filter-repo 에 rewrite 되고, 성공 후에도 repo 에 남아 쓰레기 ref 가 됨. v1.2 부터는 **bundle 파일만** 사용. tag 는 만들지 않는다.

```bash
TIMESTAMP=$(date +%Y%m%d-%H%M%S)
BUNDLE="/c/tmp/backup-commit-edit-${TIMESTAMP}.bundle"
mkdir -p /c/tmp

git bundle create "$BUNDLE" --all
```

- bundle 파일 경로를 **반드시 보고에 포함**. 사용자가 이 파일만 있으면 언제든 복원 가능
- bundle 생성 실패하면 중단 (롤백 수단이 없으므로)
- bundle 에서 복원: `git clone "$BUNDLE" /c/tmp/restore-<TS>` 또는 현 repo 에 `git fetch "$BUNDLE" 'refs/heads/*:refs/heads/backup-*'`
- **repo 에 `backup/commit-edit/*` tag 등 ref 를 만들지 않는다** (작업 흔적을 main 에 남기지 않기 위해)

### 3.2 작업 공간 선택 (두 경로)

#### 경로 A (권장, 최고 안전): 격리 clone 에서 작업

원본 repo 를 **건드리지 않고** 별도 폴더에서 rewrite 후, 결과만 원본으로 반영.

```bash
WORK="/c/tmp/commit-edit-workdir-${TIMESTAMP}"
git clone . "$WORK"                    # 또는 bundle 에서 clone
cd "$WORK"
git remote remove origin               # clone 시 원본 경로가 origin 으로 잡히므로 제거
# 이후 §4 편집 + §5 검증을 $WORK 안에서만 수행
```

검증 통과 후 반영:
```bash
# 원본 repo 로 돌아와서 $WORK 의 main 을 가져옴
cd <원본 repo>
git remote add scratch "$WORK"
git fetch scratch
git checkout main
git reset --hard scratch/main
git remote remove scratch
```

원본 repo 는 필터링 작업 중 전혀 영향 받지 않음. 가장 안전.

#### 경로 B (in-place, 빠르지만 위험): edit 브랜치 + `--refs` 제한

원본 repo 에서 직접 edit 브랜치로 분리하고 filter-repo 의 `--refs` 옵션으로 범위 제한.

```bash
TOPIC="<짧은 설명, 예: msg-fix-abc1234>"
git checkout -b "commit-edit/${TIMESTAMP}-${TOPIC}"
```

**주의:** `--refs HEAD` 를 명시해도 filter-repo 는 encoding·gpgsig 정규화로 **조상 commit 까지 SHA 가 재기록**될 수 있음. 원본 repo 의 다른 branch·tag 에는 영향 없지만, remote-tracking (origin/*) 과 reflog 는 모두 제거됨. bundle 백업이 없으면 사고 시 복구 불가.

경로 B 사용 조건: 개인 repo, 다른 클론 없음, 빠른 작업 선호, force-push 수용 가능. 불확실하면 경로 A 택하기.

## 4. 편집 도구 선택

수정 대상 위치·복잡도에 따라 도구 분기:

### 4.1 HEAD 커밋 메시지/body 수정 -> `git commit --amend`

가장 단순. tree 변경 없으면 `--amend` 가 author 정보 보존, committer date 만 갱신됨 -> env var 로 명시 보존.

```bash
# 원본 author/committer date 추출
ORIG_AD=$(git log -1 --format=%aI HEAD)
ORIG_CD=$(git log -1 --format=%cI HEAD)

# 메시지만 교체 (tree 변경 없음)
GIT_COMMITTER_DATE="$ORIG_CD" \
  git commit --amend --date="$ORIG_AD" -m "<새 메시지>"

# 또는 body 포함 다중 -m
GIT_COMMITTER_DATE="$ORIG_CD" \
  git commit --amend --date="$ORIG_AD" \
    -m "<제목>" \
    -m "<body 단락 1>" \
    -m "<body 단락 2>"

# 또는 HEREDOC 한 줄 메시지로 (개행 보존)
GIT_COMMITTER_DATE="$ORIG_CD" \
  git commit --amend --date="$ORIG_AD" -m "$(cat <<'EOF'
<제목>

<body 본문>
EOF
)"
```

확인: `git log -1 --format='%H %an %aI %cI %s'` 로 author/committer date 가 보존됐는지 검사.

### 4.2 과거 커밋 메시지/body 만 수정 -> `git filter-repo --replace-message`

`git-filter-repo` 가 이미 설치돼 있음. 메시지·body 만 바꾸고 author·date·tree 는 보존. 다중 커밋 일괄 치환에 유리.

**전제:** §3.1 bundle 백업이 완료되어 있어야 함. §3.2 경로 A(격리 clone) 또는 경로 B(in-place + edit 브랜치) 안에서 실행.

```bash
# 1. 치환 규칙 파일 작성 (literal 매칭, ==> 로 구분)
cat > /c/tmp/commit_edit_replacements.txt <<'EOF'
docs: 책재구성 v1.1 존댓말 규칙 + 책검토 스킬 v1.0 신설==>📝 docs: 책재구성 v1.1 존댓말 규칙 + 책검토 스킬 v1.0 신설
EOF

# 2. filter-repo 실행. --refs HEAD 로 현재 브랜치만 처리하도록 제한 필수
git filter-repo --replace-message /c/tmp/commit_edit_replacements.txt --refs HEAD --force
```

- `--refs HEAD` **누락 시 모든 ref(백업 태그 포함)가 rewrite 됨**. 이 옵션은 v1.1에서 필수화
- `--force` 는 "non-fresh clone" 경고 우회. 격리 clone 이면 불필요할 수도 있지만 일반적으로 붙임
- 치환 파일 한 줄 = 한 규칙. `OLD==>NEW` literal 매칭 (정규식 쓰려면 `regex:` prefix)
- filter-repo 는 author date·committer date·tree 는 자동 보존
- 그러나 다음은 영향 받음:
  - **모든 remote-tracking branch 제거** (origin/* 등) -> 추후 `git fetch origin` 으로 복원
  - **origin remote 자체 제거** -> `git remote add origin <URL>` 로 재등록
  - **reflog 비워지고 GC 자동 실행** -> 원본 객체 로컬 복구 불가 (bundle 만 믿음)
  - **조상 commit SHA 까지 재기록** (encoding·gpgsig 정규화). `--refs HEAD` 로 제한해도 현재 브랜치 범위 안에서는 전부 새 SHA. origin 에 push 된 과거 commit 도 force-push 해야 동기화

### 4.3 과거 커밋 + 복잡 변경 -> cherry-pick 재구성 (fallback)

filter-repo 로 표현 못 하는 변경(예: 여러 커밋 중 특정 하나만 body 구조 전면 개편)은 수동 재구성:

```bash
TARGET=<수정 대상 SHA>
PARENT=$(git rev-parse "${TARGET}^")

# 1. PARENT 까지 reset
git reset --hard "$PARENT"

# 2. TARGET 의 변경분만 staging (커밋 안 함)
git cherry-pick --no-commit "$TARGET"

# 3. 새 메시지로 커밋, 원본 author/committer date 보존
ORIG_AD=$(git log -1 --format=%aI "$TARGET")
ORIG_CD=$(git log -1 --format=%cI "$TARGET")
ORIG_AN=$(git log -1 --format=%an "$TARGET")
ORIG_AE=$(git log -1 --format=%ae "$TARGET")

GIT_AUTHOR_NAME="$ORIG_AN" \
GIT_AUTHOR_EMAIL="$ORIG_AE" \
GIT_AUTHOR_DATE="$ORIG_AD" \
GIT_COMMITTER_DATE="$ORIG_CD" \
  git commit -m "<새 메시지>"

# 4. TARGET 이후 커밋들 순서대로 cherry-pick (committer date 보존)
for sha in $(git log "${TARGET}..backup/commit-edit/${TIMESTAMP}" --reverse --format=%H); do
  ORIG_CD=$(git log -1 --format=%cI "$sha")
  GIT_COMMITTER_DATE="$ORIG_CD" git cherry-pick "$sha"
done
```

- cherry-pick 충돌 발생 시 즉시 멈추고 사용자에게 보고 (자동 해결 시도하지 않음)
- 충돌 발생은 보통 타깃 이후 커밋이 같은 라인을 건드린 경우. 해결책 함께 제시

## 5. 검증

rewrite 직후 main 적용 전, bundle 백업과 비교해서 의도하지 않은 변경이 없는지 확인.

### 5.1 range-diff (필수, range form 사용)

**v1.0 결함:** `git range-diff <tag> HEAD` 는 single-commit form 이면 `fatal: need two commit ranges`. 반드시 range form 사용.

```bash
# 변경 대상 커밋 수 N (예: 최근 10개 수정이면 N=10, 여유있게 +α)
N=<rewrite 대상 커밋 수 + 여유>

# 1. bundle 기반: bundle 에서 참조 branch 뽑아서 비교
git fetch "$BUNDLE" 'refs/heads/main:refs/heads/_backup_main'
git range-diff "_backup_main~${N}..refs/heads/_backup_main" "HEAD~${N}..HEAD"
# 확인 후 임시 ref 정리
git branch -D _backup_main

# 2. 또는 filter-repo 의 commit-map 기반 1:1 비교 (range-diff 가 불가능할 때 대체)
cat .git/filter-repo/commit-map | while read old new; do
  [ "$old" = "old" ] && continue  # 헤더 건너뛰기
  [ -z "$old" ] && continue
  old_subject=$(git show --no-patch --format=%s "$old" 2>/dev/null || echo "MISSING")
  new_subject=$(git show --no-patch --format=%s "$new")
  old_tree=$(git show --no-patch --format=%T "$old" 2>/dev/null || echo "MISSING")
  new_tree=$(git show --no-patch --format=%T "$new")
  tree_ok=$([ "$old_tree" = "$new_tree" ] && echo "OK" || echo "CHANGED")
  echo "$old -> $new | tree:$tree_ok | $old_subject => $new_subject"
done
```

기대 출력: 메시지 변경된 커밋만 변경 표시. 다른 커밋은 `=` 또는 tree:OK. 메시지 외 부분(tree CHANGED)이 있으면 즉시 중단.

### 5.2 tree 동일성 (선택, 강한 확인)

각 커밋의 tree hash 가 동일한지 비교:

```bash
diff \
  <(git log "backup/commit-edit/${TIMESTAMP}" --reverse --format='%T %s') \
  <(git log HEAD --reverse --format='%T %s') \
  | head -50
```

tree hash 가 다르면 파일 내용이 바뀐 것. 메시지만 수정 의도였다면 이건 회귀.

### 5.3 커밋 개수 동일성

```bash
COUNT_BACKUP=$(git rev-list --count "backup/commit-edit/${TIMESTAMP}")
COUNT_NEW=$(git rev-list --count HEAD)
echo "backup: $COUNT_BACKUP, new: $COUNT_NEW"
```

다르면 어딘가에서 커밋이 사라지거나 추가된 것. 즉시 중단.

### 5.4 검증 실패 시

- 절대 main 에 적용하지 않음
- edit 브랜치 폐기 검토: `git checkout main && git branch -D commit-edit/...`
- bundle 파일은 그대로 보존 (main 은 손대지 않았으므로 복구 불요, 안전판)
- 사용자에게 실패 원인 보고

## 6. 사용자 보고 + 적용 승인

### 6.1 보고 형식

검증 통과 후 사용자에게 다음 형식으로 보고:

```
[커밋수정 검증 완료]

대상: <SHA(들)>
bundle 백업: /c/tmp/backup-commit-edit-<TIMESTAMP>.bundle
edit 브랜치: commit-edit/<TIMESTAMP>-<TOPIC>

변경 요약:
- <SHA1> 메시지: '<old>' -> '<new>'
- <SHA2> body: <변경 요약>

검증 결과:
- range-diff: 메시지 외 변경 없음 ✓
- tree 동일성: 모든 커밋 tree hash 일치 ✓
- 커밋 개수: <N>개 동일 ✓

push 상태:
- 대상 커밋 origin 에 push 됨 -> main 적용 후 force-push 필요
  (또는: local only -> push 불요)

다음 단계 (선택):
A. main 에 적용하고 force-push (origin/main 갱신, 다른 클론에 영향)
B. main 에만 적용 (push 보류)
C. edit 브랜치 그대로 두고 사용자 직접 검토
D. 폐기 (edit 브랜치 삭제, bundle 파일은 보존)

어느 옵션으로 진행할까요?
```

### 6.2 사용자가 A 또는 B 선택 시 main 적용

```bash
# main 으로 이동
git checkout main

# edit 브랜치로 main 을 fast-forward (실제로는 hard reset)
git reset --hard "commit-edit/${TIMESTAMP}-${TOPIC}"
```

### 6.3 force-push (옵션 A 만)

```bash
# 반드시 --force-with-lease (다른 사람 push 가 위에 쌓였으면 거부)
git push --force-with-lease origin main
```

push 실패 시:
- `--force-with-lease` 가 막은 거면 다른 사람 push 가 origin 에 있다는 뜻 -> 자동 진행 금지
- 사용자에게 상황 보고하고 원격 변경 fetch/검토 후 결정

## 7. 정리 + 최종 보고

### 7.1 edit 브랜치 정리 (선택)

main 적용 후 edit 브랜치는 더 이상 필요 없음. 사용자가 명시적으로 정리 요청하면:

```bash
git branch -D "commit-edit/${TIMESTAMP}-${TOPIC}"
```

### 7.2 bundle 파일 보존

bundle 파일(§3.1)은 사용자가 명시적으로 삭제 요청할 때까지 보존. repo 안에는 작업 흔적(태그 등) 을 남기지 않으므로 `git tag` 나 `git branch` 에 작업 관련 항목이 남아있으면 안 됨.

보고에 롤백 명령 안내:

```
bundle 백업: /c/tmp/backup-commit-edit-<TIMESTAMP>.bundle (보존)

롤백 필요 시:
  # 1. bundle 을 임시 브랜치로 fetch
  git fetch "/c/tmp/backup-commit-edit-<TIMESTAMP>.bundle" 'refs/heads/main:refs/heads/_restore_main'

  # 2. main 을 그 지점으로 reset
  git checkout main
  git reset --hard _restore_main
  git branch -D _restore_main

  # 3. origin 에 push 됐었다면 force-push (사용자 명시 승인 후)
  git push --force-with-lease origin main

bundle 파일 정리는 충분한 시간 지난 후 사용자 명시 요청 시:
  rm "/c/tmp/backup-commit-edit-<TIMESTAMP>.bundle"
```

### 7.3 최종 보고

```

수정된 커밋: <new SHA>(s)
이전 커밋: <old SHA>(s) -> bundle 파일에서만 접근 가능
적용: main 갱신 [O], origin push [O/X]
bundle 파일: /c/tmp/backup-commit-edit-<TIMESTAMP>.bundle (보존)

다음 작업이 있으면 알려주세요.
```

## 8. 안전 규칙·금지사항 (요약)

| 규칙 | 이유 |
|---|---|
| **bundle 파일** 백업 없이 rewrite 시작 금지 | 롤백 불가능 |
| 백업용 tag·branch 생성 금지 | repo 에 작업 흔적 남기지 않음. bundle 파일이면 충분 |
| filter-repo 명령에 `--refs HEAD` 누락 금지 | 모든 ref 영향 |
| `git rebase -i` 금지 | 환경 제약 (interactive 입력 불가) |
| `--no-verify`, `--no-gpg-sign` 금지 | hook·서명 우회 (CLAUDE.md 규정) |
| `git push --force` 금지 | `--force-with-lease` 만 사용 |
| 사용자 승인 없는 main reset/force-push 금지 | shared state 변경 |
| 검증 단계 건너뛰기 금지 | tree 회귀 미검출 위험 |
| bundle 파일 임의 삭제 금지 | 사용자 명시 요청 시만 |
| 작업 완료 후 edit 브랜치 남기기 금지 | main 에 적용됐으면 `git branch -D` 로 정리 |
| 새 메시지에 키보드 미입력 특수문자 사용 금지 | 메모리 컨벤션 (gitmoji 제외) |
| 새 메시지는 `<emoji> <type>(<scope>): <subject>` 형식 강제 | 메모리 컨벤션 |

## 9. 트러블슈팅

### 9.1 amend 했는데 author date 가 today 로 바뀜

`--date` 옵션 누락. amend 시 `--date="$ORIG_AD"` 명시 필요. bundle 파일에서 다시 시도.

### 9.2 amend 했는데 committer date 가 today 로 바뀜

`GIT_COMMITTER_DATE` env var 누락. amend 는 committer date 를 자동 보존하지 않음. bundle 파일에서 다시 시도.

### 9.3 filter-repo 실행 후 부작용 (중요)

filter-repo 는 "fresh clone 전제" 철학으로 다음을 자동 수행. 예상 못 하면 "안전 보험"이 무너짐.

- **모든 ref rewrite**: `--refs` 미지정 시 모든 branch·tag·remote-tracking 이 rewrite 대상. 백업 태그도 예외 없음 -> `--refs HEAD` 명시로 제한하고 bundle 백업 병행
- **remote-tracking branch 제거**: `refs/remotes/*` 전부 사라짐 -> `git fetch <remote>` 로 복원
- **origin remote 제거**: `git remote add origin <URL>` 로 재등록
- **reflog 전체 비워짐**: `git reflog` 에 남아있던 복구 지점 사라짐
- **GC 자동 실행**: 원본 commit 객체가 즉시 수거되어 `git cat-file -t <old-sha>` 가 `could not get object info` 반환. 로컬에서는 복구 불가
- **조상 commit SHA 재기록**: 메시지가 매칭되지 않은 commit 도 encoding·gpgsig 정규화로 SHA 가 바뀜. 현재 branch 의 모든 commit 이 새 SHA. origin 과 fast-forward 불가능 -> force-push 필수

복구가 필요해지면 §3.1 bundle 파일에서 복원:
```bash
git clone "/c/tmp/backup-commit-edit-${TIMESTAMP}.bundle" /c/tmp/restore-<TS>
# 또는 현재 repo 에 편입:
git fetch "/c/tmp/backup-commit-edit-${TIMESTAMP}.bundle" 'refs/heads/*:refs/heads/_restore_*'
```

### 9.4 cherry-pick 충돌

같은 파일·라인을 후속 커밋이 건드린 경우. 자동 해결 시도하지 않고 사용자에게 보고. 사용자가 충돌 해결하면 `git cherry-pick --continue` 로 진행 (단, 이 경우에도 GIT_COMMITTER_DATE env 는 잃어버리므로 별도 amend 로 보정 필요).

### 9.5 push 가 `--force-with-lease` 로 거부됨

origin 에 다른 push 가 쌓인 것. `git fetch origin` 으로 가져와서 사용자에게 상황 보고. 절대 `--force` 로 덮어쓰지 않음.

### 9.6 검증 실패 (tree 변경 감지)

rewrite 도구 사용 중 의도치 않은 tree 변경 발생. edit 브랜치 폐기하고 bundle 파일에서 다시 시작. 어떤 단계에서 변경이 들어갔는지 사용자와 함께 분석.

## 10. 빠른 명령 모음

가장 흔한 케이스 한 줄 명령:

### HEAD 커밋 메시지만 교체
```bash
TS=$(date +%Y%m%d-%H%M%S) && \
mkdir -p /c/tmp && \
git bundle create "/c/tmp/backup-commit-edit-$TS.bundle" --all && \
ORIG_AD=$(git log -1 --format=%aI HEAD) && \
ORIG_CD=$(git log -1 --format=%cI HEAD) && \
GIT_COMMITTER_DATE="$ORIG_CD" git commit --amend --date="$ORIG_AD" -m "<새 메시지>"
```

### 과거 커밋 메시지 일괄 치환 (filter-repo, 경로 B in-place)
```bash
TS=$(date +%Y%m%d-%H%M%S) && \
mkdir -p /c/tmp && \
git bundle create "/c/tmp/backup-commit-edit-$TS.bundle" --all && \
git checkout -b "commit-edit/$TS-bulk-msg" && \
echo "<old>==><new>" > /c/tmp/replacements.txt && \
git filter-repo --replace-message /c/tmp/replacements.txt --refs HEAD --force && \
git remote add origin https://github.com/siakun-private/obsidian-personal.git && \
git fetch origin
```

이후 §5 검증 -> §6 사용자 승인 -> §7 적용.

### 과거 커밋 메시지 일괄 치환 (경로 A, 격리 clone 권장)
```bash
TS=$(date +%Y%m%d-%H%M%S) && \
mkdir -p /c/tmp && \
git bundle create "/c/tmp/backup-commit-edit-$TS.bundle" --all && \
WORK="/c/tmp/commit-edit-workdir-$TS" && \
git clone . "$WORK" && \
cd "$WORK" && \
git remote remove origin && \
echo "<old>==><new>" > /c/tmp/replacements.txt && \
git filter-repo --replace-message /c/tmp/replacements.txt --refs HEAD --force
```

검증 후 원본 repo 로 돌아가서:
```bash
cd <원본 repo>
git remote add scratch "$WORK"
git fetch scratch
git checkout main
git reset --hard scratch/main
git remote remove scratch
git push --force-with-lease origin main  # 사용자 승인 후
```
